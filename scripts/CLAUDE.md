# scripts

**Book:** `docs/src/compat/verification.md`. Read them for the design, and update them in the same commit when behaviour here changes.

`scripts/kafka-*.sh` (at the repo root) is a per-tool integration suite that runs the Apache Kafka shell tools (`kafka-topics`, `kafka-{producer,consumer}-perf-test`, `kafka-acls`, etc.) against a live broker — *not* invoked by `cargo test`. Each script sources `scripts/_common.sh` for shared `BOOTSTRAP` / `KAFKA_BIN` / `skip` helpers; defaults target the in-cluster Service DNS and `/opt/kafka/bin`. The live cluster has no anonymous listener, so `_common.sh` authenticates every tool call: it builds `CLIENT_PROPS` from the `kaas-scripts` KafkaUser's Secret and points `KAFKA_BIN` at wrappers that add `--command-config` — write new scripts as plain Kafka CLI calls and they inherit it. Scripts that target features that are non-goals or post-3.7 (KRaft tools, share-groups, etc.) print a one-line reason and `exit 77` (the autoconf "skipped" code) so they're discoverable without pretending to test something that can't work. **A script that deliberately disturbs the cluster must call `wait_cluster_ready` (in `_common.sh`) before it returns** — the suite runs sequentially, so an unsettled cluster is inherited by whatever script sorts next. `kafka-restart-resilience.sh` is the only such script today; it bounces a broker mid-produce, and leaving it unsettled produced `FIND_COORDINATOR` timeouts in the script that followed. Waiting on the bounced pod alone is not enough on either axis: `delete --wait=false` plus a grace period leaves the outgoing pod Running and Ready, so `kubectl wait --for=condition=ready` matches the old incarnation and returns instantly (compare `metadata.uid` to see the replacement), and the bounce moves partitions *and* group coordinators onto the survivors, which settle independently of the restarted pod.

**The Kafka tools' exit codes and stdout say less than they seem to.** `kafka-console-consumer` exits 0 on a timeout and also on an unreachable broker, with no output, so an empty result only means something once a scenario has read records from that bootstrap. `kafka-producer-perf-test` exits 0 even when every record fails. The 4.x CLI writes deprecation notices to stdout, so a line count takes one for a record: compare the records themselves, and use flags that aren't deprecated. A count passes wrong records too; if payloads are random and it has to count, leave off `--max-messages`, which hides extras. A check that only prints `WARN` can't fail. **Prove a scenario isn't vacuous**: a `read_committed` read of a topic with no transactions passes with the isolation level ignored, so scenario 5 of `kafka-console-consumer.sh` checks the log end for commit markers first. Break each check on purpose once, and confirm the script fails. **Cleanup belongs in an EXIT trap.** A script that deletes its topic as its last step leaks it whenever it fails; replace `_common.sh`'s trap with a superset, as `kafka-console-consumer.sh` and `kafka-acls.sh` do.
