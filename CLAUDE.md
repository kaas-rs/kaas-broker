# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

kaas is a Rust workspace: `Cargo.toml` at the root, `rust-toolchain.toml` (pin = 1.97), 12 lib crates under `crates/kaas-*`, 2 bins under `bins/{kaas,kaas-operator}`, and an `xtask` runner. `protoc` is vendored via `tonic-build` in `kaas-broker`. `proto/`, `deploy/`, and `scripts/` live at the root (tonic-build consumes `proto/heartbeat.proto`; the Helm chart and shell integration suite target the broker's wire surface). System-level architecture lives in the documentation book's Part I (`docs/src/architecture/`; build with `cargo xtask docs`, preview with `cargo xtask docs --serve` — `docs/ARCHITECTURE.md` is a pointer stub). The release line is `v0.3.x-preview` (see [`docs/RELEASING.md`](./docs/RELEASING.md); `v0.3.0-preview` added SASL/OAUTHBEARER, minor-bumped from the `v0.2.x` patch line); how the book is built, gated, and published is [`docs/README.md`](./docs/README.md). `docs-publish.yml` deploys the book to this repo's own Pages site at `kaas-rs.github.io/kaas-broker/`. The landing page at `kaas.rs` is an independent site in `kaas-rs/kaas-landing-page` that links here by absolute URL — the two share no build, and re-coupling them (one domain serving both) would require a credentialed cross-repo handoff, which was tried and removed. The only cross-repo contract is that the landing page deep-links `index.html` + `getting-started.html`; the `docs` CI job guards those.

## Parity target & non-goals

kaas targets **Apache Kafka 3.7** for wire-protocol and Kafka Streams parity. Behaviour is verified against the matrix tracked in the [kaas-migration-parity](https://github.com/users/Woestebanaan/projects/2) GitHub project. When a feature is ambiguous, default to "match Apache Kafka 3.7" rather than inventing kaas-specific semantics.

- **Deliberate post-3.7 exception:** DescribeCluster **v2** (KIP-1073,
  `IncludeFencedBrokers` / `IsFenced`) is served, because kaas has a real
  fenced state (gh #249) and no other way to report it. This is the only
  such exception; adding another needs the same explicit justification.
- **Deferred (intended later, not now):** tiered storage / S3 backend. Skip the tiered-storage-only API surfaces (e.g. `EARLIEST_LOCAL_TIMESTAMP`, `EARLIEST_PENDING_UPLOAD_OFFSET`) — clients only request them when configured for remote tiers.
- **Non-goals (off the table by design):** KRaft / metadata quorum (kaas uses K8s Leases instead), replication / ISR (single-writer-per-partition), and a literal `__transaction_state` internal topic (kaas uses per-broker JSON slot files on the shared NFS PVC — see "Idempotent producer" + "Transaction coordinator state machine" below; gh #29). Don't add any of these; flag if a "parity" task implicitly requires them.

### CI

`.github/workflows/ci.yml` runs three jobs in parallel:

- `rust` — `cargo fmt --check` + `cargo clippy -D warnings` + `cargo test --workspace --all-features` + `cargo build --release --workspace --bins` + `cargo xtask check-crd-drift` + `cargo xtask check-docs-drift`.
- `docker` — buildx of `bins/kaas/Dockerfile` and `bins/kaas-operator/Dockerfile`, no push.
- `helm` — `helm lint deploy/helm/kaas` + `helm template`.

`.github/workflows/docker-publish.yml` is tag-triggered: it builds the broker + operator images from `bins/*/Dockerfile`, pushes them to `ghcr.io/kaas-rs/kaas[-preview]` / `kaas-operator[-preview]`, and pushes the Helm chart to `oci://ghcr.io/kaas-rs/charts`.

**CRD drift** — if you edit anything under `crates/kaas-operator-api/`, run `cargo xtask gen-crds` and commit both `deploy/crds/` and `deploy/helm/kaas/crds/`. The `rust` CI job fails on drift.

Releases are tag-driven; see [`docs/RELEASING.md`](./docs/RELEASING.md). **Always bump the patch (`v0.2.N-preview` → `v0.2.N+1-preview`), never re-cut a tag.** **No backwards compatibility before v1, with one carve-out** (owner decision, 2026-07-23): a release that leaves CRD schemas **unchanged** must support an in-place rolling update from the immediately preceding preview (adjacent-version heartbeat/state/wire contracts keep working). A release that **changes CRDs** may break anything — delete-and-redeploy is its supported upgrade path; note the break in the tag message. Don't spend effort on migration shims, legacy-layout adoption, or deep mixed-version guards beyond the adjacent-release roll.

`scripts/kafka-*.sh` (at the repo root) is a per-tool integration suite that runs the Apache Kafka shell tools (`kafka-topics`, `kafka-{producer,consumer}-perf-test`, `kafka-acls`, etc.) against a live broker — *not* invoked by `cargo test`. Each script sources `scripts/_common.sh` for shared `BOOTSTRAP` / `KAFKA_BIN` / `skip` helpers; defaults target the in-cluster Service DNS and `/opt/kafka/bin`. The live cluster has no anonymous listener, so `_common.sh` authenticates every tool call: it builds `CLIENT_PROPS` from the `kaas-scripts` KafkaUser's Secret and points `KAFKA_BIN` at wrappers that add `--command-config` — write new scripts as plain Kafka CLI calls and they inherit it. Scripts that target features that are non-goals or post-3.7 (KRaft tools, share-groups, etc.) print a one-line reason and `exit 77` (the autoconf "skipped" code) so they're discoverable without pretending to test something that can't work. **A script that deliberately disturbs the cluster must call `wait_cluster_ready` (in `_common.sh`) before it returns** — the suite runs sequentially, so an unsettled cluster is inherited by whatever script sorts next. `kafka-restart-resilience.sh` is the only such script today; it bounces a broker mid-produce, and leaving it unsettled produced `FIND_COORDINATOR` timeouts in the script that followed. Waiting on the bounced pod alone is not enough on either axis: `delete --wait=false` plus a grace period leaves the outgoing pod Running and Ready, so `kubectl wait --for=condition=ready` matches the old incarnation and returns instantly (compare `metadata.uid` to see the replacement), and the bounce moves partitions *and* group coordinators onto the survivors, which settle independently of the restarted pod.

**The live cluster (`k3s-cluster`, `apps/kaas` + the `apps/strimzi` reference) has no anonymous listener and enforces ACLs.** Both clusters serve the same three TLS listeners under the same names and ports — `mtls` 9093 (client certificate), `scram` 9095 (SASL/SCRAM-SHA-512), `oauth` 9096 (SASL/OAUTHBEARER, EntraID) — so a client moves between them by changing only the host. kaas's `mtls` trusts the shared Kafka clients CA (cert-manager `kafka-clients-ca-issuer`) through the chart's per-listener `clientCA` (v0.3.8+), which arms certificate verification on that listener alone; Strimzi's uses its own clients CA. Both run `authorization: simple` with no super users. Every client is a named KafkaUser (`apps/*/kafka-users/`): `kafka-bench` (bench Jobs, `kperf-*`), `kafka-streams` (streams tests), `throttled-user` (quota benches), `kafbat-ui` / kaas-ui (all-access UIs), `kafka-connect` (Strimzi only), `kaas-scripts` (this repo's `scripts/`, admin). Jobs don't carry credentials inline: an ExternalSecret per namespace (`kafka-bench-client`, `kafka-streams-client`) renders ready-to-mount `client.properties` / `consumer.properties` / StreamsConfig from the generated password + broker CA. So a new in-cluster client needs a KafkaUser with ACLs *and* a mounted client config — a bare `--bootstrap-server` call will hang on the TLS/SASL handshake rather than fail fast. The `.claude/skills/bench-*` scripts mount those same Secrets into their throwaway `kubectl run` pods.

**Resetting a git-managed topic (e.g. `kperf-bench`) is delete-CR → wait → re-sync, not delete-and-recreate by name.** Delete the `KafkaTopic` CR on each cluster (kaas's topic watch abandons the partitions and the operator reclaims the directory; Strimzi's topic operator deletes the topic), confirm the topic is gone from the brokers, wait **2 minutes**, then re-sync the CR from ArgoCD. The wait lets kaas's reclaim finish — rename aside, recreate the partition dirs, `remove_dir_all` the staged copy — before the new incarnation's CR arrives; recreating inside that window is the gh #219 / gh #241 stale-directory territory. Check afterwards that `status.topicId` changed and every partition's latest offset is 0.

## Architecture

kaas is a from-scratch Kafka-protocol-compatible broker that runs on Kubernetes. Two binaries ship in this repo:

- **`bins/kaas`** — the broker. Listeners are declared via the `KAAS_LISTENERS` JSON env (gh #126); the chart emits one entry per `.Values.listeners[]` item. Fixed ports: 8080 health, 9094 inter-broker heartbeat gRPC.
- **`bins/kaas-operator`** — an operator that reconciles 3 CRDs into on-disk config files (auth/topics) and Kubernetes plumbing (TLS routes, etc.).

### Brokers are runtime-independent of the operator

This is the most important architectural fact and is easy to misread from the directory layout. The operator is a **startup/admission** component, not a hot-path dependency:

- Operator manages 3 CRDs typed in `crates/kaas-operator-api/src/`: `KafkaCluster` (external listener plumbing), `KafkaTopic` (partition dir creation; `Status.TopicID` carries a v4 UUID generated on first reconcile — wire propagation is still open, see "TopicID propagation" below; gh #105/KIP-516), `KafkaUser` (auth + ACLs + quotas — `spec.authentication` / `spec.authorization` mirror Strimzi 1:1 since gh #135; materialized to `credentials.json` + `acls.json` under `/data/__cluster/`. **`spec.authentication` is optional (gh #42): an authorization-only user omits it** — an OAUTHBEARER principal has no credential to materialize, so its CR carries only `authorization`/`quotas` and names the principal via `metadata.name` (the token `sub`); the reconciler writes no `credentials.json` entry and only rebuilds ACLs, matching Strimzi's authorization-only oauth users). The `KafkaClusterAssignments` CR that once existed as a reserved debug mirror was removed in v0.3.2-preview — its status writer was never ported from Go (gh #191/#262); read `assignment.json` on the volume instead. **`spec.quotas` intentionally diverges from Strimzi**: the byte-rate fields are named `producerMaxByteRatePerBroker` / `consumerMaxByteRatePerBroker` (vs Strimzi's `producerByteRate` / `consumerByteRate`) to make the per-broker semantics (Apache Kafka 3.7 / KIP-13) legible at the CR level. With N brokers the effective cluster-wide ceiling is N × the configured value — same semantics Strimzi/Apache Kafka have, just named honestly. The pre-gh #135 `KafkaACL` and `KafkaUserGroup` CRs are gone — ACLs are authored inline on each KafkaUser's `spec.authorization.acls` list. To grant the same rule to N principals, repeat the ACL on each of their KafkaUser CRs (no group abstraction; the Strimzi-pattern trade).
- Brokers read `KafkaTopic` CRs at startup (and watch them for new topics / partition expansion), but the read is non-fatal — a missing/unreachable API server only blocks new topic creation, never serving of existing topics.
- The Produce/Fetch hot path makes **zero K8s API calls**. Ownership lookups are in-memory.
- **Admin handlers DO patch `KafkaTopic` CRs** (gh #52, gh #9, gh #236). `CreatePartitions` (key 37, KIP-195) and `IncrementalAlterConfigs` (key 44, KIP-339) route through `crates/kaas-broker/src/topic_cr_writer.rs`: partition expansion patches `spec.partitions`; config updates patch `spec.config` per-key (SET/DELETE only — APPEND/SUBTRACT return `UNSUPPORTED_VERSION`; unknown keys / unparseable values return `INVALID_CONFIG` (40) — **the API server silently prunes unknown merge-patch fields, so anything not rejected client-side becomes a success that does nothing**, which was gh #236's dangerous half). `CreateTopics` (key 19) lands its wire config overrides in the minted CR's `spec.config`, same validation. The operator then materialises the change as usual, and `DescribeConfigs` (key 32) reports stored overrides as `DYNAMIC_TOPIC_CONFIG` by re-reading `.config.json` through `StorageEngine::topic_config` per request (hot-reload, like the retention sweep). **Broker RBAC includes `update,patch` on `kafkatopics`** — if you add another admin write path, check `deploy/helm/kaas/templates/broker-rbac.yaml` doesn't need a new verb. `IncrementalAlterConfigs` is TOPIC-only; BROKER / BROKER_LOGGER resource types return `UNSUPPORTED_VERSION` (no dynamic broker-config surface yet). Broker-**created** CRs optionally carry ArgoCD tracking/coexistence annotations (`crates/kaas-broker/src/argocd.rs`, chart `admin.argocd.*` → `KAAS_ARGOCD_*` env; gh #84/#106 re-ported from Go) — creation only: the ACL writer edits *existing* `KafkaUser` CRs and must never stamp ArgoCD metadata on a git-managed resource.

**Operator reconcilers do NOT use cleanup finalizers.** Earlier versions had `kaas.rs/{topic,user,acl,usergroup,kafkacluster}-cleanup` finalizers that drained on CR delete; ArgoCD's parallel cascade-delete deadlocked when the operator pod went down before its CRs. Cleanup is now reconcile-time (best-effort recursive delete / credentials-file edit when the CR is gone) plus a leader-elected startup sweep (`crates/kaas-operator-controllers/src/`) that drops orphan dirs / stale credential entries the reconciler missed. Owned external resources (Certificates, Services, TLSRoutes) carry `OwnerReferences` so K8s GC handles cluster-CR deletion.

If you find yourself adding a runtime dependency from broker → operator (e.g. a watch on a CR that blocks request handling), stop — that's an architectural change.

### Controller broker, leases, and the authoritative assignment file

The "controller" is **a broker that holds the `kaas-controller` Lease**, not a separate process. Its responsibilities:

- Observes peer brokers via gRPC heartbeats (`proto/heartbeat.proto`, tonic-build output in `kaas-broker`, `crates/kaas-controller/src/heartbeat_server.rs`).
- Computes partition + consumer-group assignments (`crates/kaas-controller/src/balancer.rs`, `assignment_writer.rs`).
- Writes `/data/__cluster/assignment.json` on the shared RWX PVC. The file is epoch-prefixed by `leaseTransitions`; brokers reject writes with stale epochs (verified by `crates/kaas-controller/tests/stale_controller_race.rs`).

`assignment.json` is the **single source of truth for partition leadership** (gh #75 cleanup). The Metadata response, the produce/fetch ownership check, and `/healthz`'s `partitions_led` all source from it via the broker `Coordinator` (`crates/kaas-broker/src/coordinator.rs`). There is no per-partition Lease — only the singleton `kaas-controller` Lease used for cluster-wide controller election. The local-lease shim (`crates/kaas-broker/src/local_lease.rs`, always "yes, I lead") exists for dev mode only.

The controller recomputes the assignment when:
- It first wins the controller Lease (initial recompute).
- A `KafkaTopic` CR is added / modified / deleted — wired via the topic-watcher's change notification (gh #74, `bins/kaas/src/cluster.rs`).
- A broker joins or leaves the alive set — wired via the broker-set watcher polling the alive set every 2 s (gh #77, `bins/kaas/src/cluster.rs`).

Non-controller brokers watch `assignment.json` via file notification + 1s poll (`crates/kaas-broker/src/coordinator.rs`); the `TakeoverDriver` / `GroupTakeoverDriver` registered on assignment change (`takeover.rs`, `group_takeover.rs`) opens or relinquishes partitions in the storage engine to match.

**The balancer is incremental, and the phase order is what makes it so (gh #206, gh #247).** `balance()` runs: pin every partition whose previous leader is still alive → place only the rest, levelling each topic across the alive set → smooth cluster-wide to `max − min ≤ 1` → smooth per-topic without disturbing that → reconcile epochs. **Preserve must stay first.** Until gh #206 it ran last: placement was pure rendezvous and `smooth_partitions` was a pure function of `(topics, alive)`, so creating or deleting *any* topic re-derived the whole layout and migrated partitions of unrelated topics — every move a real open/recover/close cycle on NFS plus a window where the outgoing leader is still acking (the gh #227 dual-writer window, whose "not just broker death" trigger was exactly this). Kafka Streams' `application-reset` deletes and recreates topics on every run, so the churn was routine. Two properties in the smoothers are deliberate: victims are chosen non-sticky-first (a freshly placed slot costs nothing to move, an inherited one costs a takeover), and the per-topic pass repairs skew by **swapping** with a partition of another topic — cluster counts are untouched by construction, so the two passes can't fight. Per-topic evenness is its own goal, not a side effect of the cluster-wide count: at 24/24/25 the cluster smoother's predicate is already false, which is how a 3-partition topic pinned all three partitions to one broker forever (gh #247). Both smoothers strictly decrease `Σ count²`, which is what bounds them.

Local-dev mode is selected when `MY_POD_NAME` is unset (`bins/kaas/src/main.rs`); in that case storage also flips to in-memory. The cluster runtime is not started in dev mode — produce and Metadata fall back to local-lease paths that always treat self as leader of every partition.

### The NFS substrate contract (governing principle)

Multi-broker mode runs on a shared RWX (NFSv4-class) volume that IS the coordination substrate. NFS gives you exactly three guarantees — same-directory `rename()` atomic, `open(O_CREAT|O_EXCL)` atomic, close-to-open consistency — and nothing else; `remove_dir_all`, read-modify-write, and check-then-act (which is `Partition::open`'s shape) are all non-atomic. So the rule for any code touching the shared volume is: **(1)** persist via `tmp + fsync + rename` (`crates/kaas-storage/src/atomic_write.rs`), never in-place; **(2)** any compound op that can't be a single atomic primitive must be idempotent and driven to completion by retry/reconcile, never one-shot; **(3)** mutate through single-writer + epoch fencing so there's no concurrent writer to race. Most historical bugs are violations: gh #203 (operator `remove_dir_all` races broker open → rule 3), gh #215 (`take_over` not retried → rule 2), gh #205 (sweep not resumable → rule 2), gh #76 (unlink-while-open silly-rename → rule 3). Full write-up + the reviewer checklist: `docs/src/architecture/nfs-substrate.md`. When adding code that writes the shared volume, run it past the three questions before shipping.

### Storage hot path & file-handle ownership

The broker's storage engine is heavily optimised for shared-NFS substrates where every NFS COMMIT round-trip is the dominant cost. The Produce path (gh #80/#81/#82) issues **one NFS COMMIT per group of concurrent batches**, not per record — a per-partition committer task drains flush requests and runs one log `sync_all()` per cycle while concurrent appenders await a condvar. The index file is **not** fsynced on the hot path (rebuildable on takeover); the manifest is **not** rewritten per Produce — it's persisted only on partition open (takeover routes through open) and on close/relinquish, so its `HighWatermark` can lag in-memory state. Segment recovery runs at takeover time and reconciles. **Recovery is bounded by a recovery checkpoint** (Kafka's recovery-point, per partition; `crates/kaas-storage/src/recovery_checkpoint.rs`): `recovery-checkpoint.json` records `{segment_base, byte_pos, high_watermark}` — the committer writes it once the fsynced log grows `CHECKPOINT_INTERVAL_BYTES` (64 MiB) past the last one, and a clean close/relinquish writes it at EOF. `Partition::open` resumes the HWM scan from `byte_pos` (`scan_high_watermark_from`) instead of byte 0 when the checkpoint names the current active segment; otherwise (missing/stale/rolled/truncated) it falls back to a full scan — always correct, cheap with a bounded `segment.bytes`. Net: a graceful restart re-scans nothing (checkpoint at EOF), a crash re-scans ≤64 MiB. The checkpoint file is a pure optimization hint — never load-bearing for correctness (**disputed — see gh #230**: it seeds the recovered HWM, so a stale one is not merely a slow path).

**The recovery scan verifies CRCs and truncates the torn tail (gh #228, gh #226).** `scan_high_watermark_from` returns a `ScanResult { high_watermark, valid_end, stop }`. It validates each batch against its own v2 CRC32C (field at batch byte 17..21, covering byte 21 onward — no record contents are read, so byte-opacity holds) and stops at the first batch that is short, structurally impossible, or fails its checksum. `Partition::open` then truncates the active log to `valid_end` **before any write handle is used**, and — the load-bearing half — resets `ActiveSegment::log_size` to it. Without that reset appends resume at the file's `stat()` length, i.e. *past* the garbage, so the log becomes `[valid][torn][new]`; the next recovery stops at the tear and every record written after it is gone, having been acked and (at `flushIntervalMessages: 1`) fsynced, with its offsets re-issued to different data. Two invariants: truncation only ever removes bytes the scan **proved** unparseable (a clean log is never touched, so a spurious size discrepancy can't destroy data), and it is bounded by the checkpoint — corruption *before* `byte_pos` is trusted, not detected. `Fs::truncate` defaults to `Unsupported` so wrapper/fake filesystems don't silently claim success; recovery stays correct there because the `log_size` reset still happens. The `KAAS_FLUSH_INTERVAL_MESSAGES` env var (default 1 = honest acks=all) is the durability/throughput dial — mirrors Apache Kafka's `log.flush.interval.messages`. Core modules: `crates/kaas-storage/src/{engine,disk,partition,segment,manifest,recovery_checkpoint}.rs`.

Segment roll splits the work: the in-memory swap (log fsync + create new active + pointer swap) runs under the partition mutex; the deferred finalize (index fsync, close old FDs) runs in a spawned task. `DeleteRecords` (API key 21) drives `logStart` advance and unlinks fully-covered *closed* segments; the active segment is never reclaimed.

**Only the partition's current leader holds open log/index file descriptors** (gh #76 follow-up). Partition open at startup stats segments without opening handles. `TakeoverDriver` calls the engine's take-over which opens handles before recovery; relinquish closes them. This makes leader-side file removal (segment retention, DeleteRecords, segment roll cleanup) actually free disk on NFS rather than silly-renaming the file because peer brokers held it open. The committer re-locks the partition mutex inside `spawn_blocking` and fsyncs while holding it (readers stay unaffected via the ArcSwap snapshot). Syncing a cloned FD outside the lock was built and measured under gh #232 and then **reverted** — it worked mechanically (writes grew +2.9%) but produced no throughput, and it is not worth the durability-critical subtlety it introduced: the published flush seq had to be the one sampled *before* the sync, an invariant no test covered and that a tidying refactor would naturally break, silently acking data as durable that may not be on disk. Don't rebuild it without first re-reading the budget below.

**Takeover raises the epoch and rolls a fresh segment — both halves are load-bearing (gh #227).** `Partition::take_over(epoch)` sets `guard.epoch = epoch`, rolls the active segment to a new epoch-stamped file, and persists the manifest *before* the partition accepts a write. Until gh #227 the engine's `take_over` discarded its `epoch` argument and nothing else advanced the epoch, so the append fence compared against 0 and passed everything, every segment carried the same epoch, and a new leader appended to the file the outgoing one still had open — two `write_at` calls at independent `log_size` values interleaving in one log. The window is not just broker death: any partition move takes leadership off a perfectly healthy broker, which keeps acking until its own `assignment.json` watch catches up. gh #206 made those moves rare (the balancer no longer reshuffles unrelated topics on every topic create/delete) but not impossible, so the fence is still what makes them safe. Three invariants to preserve: take-over is **idempotent at or below the current epoch** (`on_change` and the gh #215 reconcile both re-drive it); a roll over an *empty* active segment lands at the same base offset, so `list_segments` keeps only the highest epoch per base offset; and `persist_state_locked` **re-reads the on-disk manifest and writes nothing if its epoch is higher** — otherwise a fenced leader's relinquish rolls the epoch back and republishes its stale HWM over its successor's. `close()` skips the recovery checkpoint on that path too, since the checkpoint seeds the recovered HWM (gh #230). **The gh #215 reconcile compares epochs, not just the open set** — because `take_over` now does work *after* the open, a failed roll/persist leaves a partition that is open (so the old open-set-only check called it converged) but still at the previous leader's epoch with the fence unarmed, and nothing re-drove it until the next assignment change. `StorageEngine::partition_epoch` answers "open at the right epoch"; an engine returning `None` (memory/dev) keeps the open-set-only semantics. **That reported epoch must stay durable-only**: `take_over` raises `guard.epoch` before the persist (the persist writes it) and puts it back if the write fails, because a raised-but-unsaved epoch reports a takeover that never finished as complete and the reconcile then skips it forever. A re-drive rolls again at the same epoch over the segment the failed attempt created, so the roll skips its outgoing-file removal when the new path is the one it already occupies. **All manifest writes go through `manifest::write_unless_superseded`** (gh #235): the epoch is the durable fence seed and no writer may lower it. Every writer reads, works, then writes back, and `Partition::open`'s gap spans a whole recovery scan — a takeover completing in it used to get replayed over, silently unarming the fence with no error and no way for the reconcile to notice (the winner's in-memory epoch stayed correct, so the partition looked converged). `open` adopts the returned epoch rather than serving below the durable one. Re-reading cannot close the window — NFS has no compare-and-swap — but identical writes are skipped outright, so a steady-state open touches the manifest not at all.

**The stale-leader ack window is bounded, not zero (gh #164).** A deposed-but-alive leader keeps accepting `acks=all` writes until its own `assignment.json` poll lands — up to ~1 s plus the NFS attribute-cache TTL, capped at 3 s by the self-fence *only* when the reassignment was caused by lost controller connectivity (a balancer-driven move off a healthy broker never trips the self-fence). During that window an acked batch lands in the old-epoch segment at offsets the new leader re-issues: the gh #227 fence guarantees the new incarnation's log is never corrupted by it, but the acked write is lost. There is no synchronous producer-side fence to close this — Apache's Produce request carries no `currentLeaderEpoch` at any version (KIP-320's field is Fetch/ListOffsets-side; the record-batch header's `partitionLeaderEpoch` arrives as -1 and is broker-stamped in Apache), so inventing one would break parity, and Apache's own equivalent window is closed by replication, a kaas non-goal. Closing it would take event-driven assignment delivery or a durable-epoch check on first write after takeover — file a scoped issue before attempting either.

**Why it was reverted, and what actually binds.**

**On a slow-fsync substrate the produce ceiling is set by how many durable writes are in flight, and almost nothing in the broker moves that number.** Throughput obeys Little's law: `concurrent writes × bytes per write ÷ write RTT`. Measured on this NAS: `4.8 × 49,617 B ÷ 16.64 ms = 14.4 MB/s`, against 14.42 MB/s actually observed — the model is exact, and at a single broker the concurrency term sat at ~5 no matter what was changed (all the measurements below are single-broker). Levers tested, all flat: broker CPU 2 → 6 cores (+0.5%), the partition mutex (gh #232, +2.9% write size, no throughput), partition count 16 → 64 (flat, and clearly worse on tail latency — it trades bytes-per-round-trip against number-of-round-trips), and client `max.in.flight.requests.per.connection` 5 → 20 with `enable.idempotence=false` (14.40 → 14.42 MB/s, i.e. nothing). The NFS transport is not the limit either: `bklog_u` is 0 cumulatively, so RPCs never wait for a slot, and the link runs at ~14% utilisation. Only `KAAS_FLUSH_INTERVAL_MESSAGES` moves the number (3.21×), and it does so by *skipping* the durability wait — see gh #212. **So the levers are lower fsync latency (faster storage) or fewer/larger writes — not broker restructuring, not more client concurrency, not more partitions.** **Broker count is the one lever that does move it, and the mechanism is not understood.** Three brokers reproducibly deliver ~1.58x a single broker — 23.13 / 23.25 MB/s across two runs on different builds versus 14.4-15.1 MB/s across four single-broker runs, both clusters tight. That is not explained by any of the above: all three broker pods share one node, hence one kernel NFS client and one transport, and raising a single broker's CPU or the client's in-flight window changed nothing. Treat multi-broker as the representative configuration for perf work, and treat the 3-vs-1 mechanism as an open question rather than assuming it is partition-leadership spread. Before optimising this path again, compute the Little's-law budget from `mountstats` (`WRITE` ops / bytes_sent / rtt on the data mount) and check which term you are actually moving.

**Graceful SIGTERM drain (gh #61, gh #139).** The shutdown path in `bins/kaas/src/main.rs` relinquishes every open partition *before* flushing manifests — persisting the manifest one last time AND closing the active segment's file handles so the next leader doesn't hit NFS silly-rename pain on takeover (partition keys are parsed from the right to handle slash-bearing topic names). There is no separate manifest-flush pass — the relinquish *is* the final persist. **There's no controlled-shutdown RPC**, but the drain is announced: `mark_draining()` before teardown rides the next heartbeat and the controller rebalances proactively — see "Broker fencing (gh #249)" below, which closed the drain-hint follow-up this section used to carry.

**`/readyz` is honest — serving-gated, not a bind-time latch (gh #208, gh #211).** `/readyz` = listeners-bound AND `main_alive()` AND (cluster mode ? `serving`). `serving` (`kaas_broker::is_serving`) means every partition `assignment.json` assigns to this broker is open in the engine — i.e. takeover is complete. It is served from a **dedicated thread + runtime** (`bins/kaas/src/main.rs`), never the main runtime it reports on, so a wedge yields readyz=unready instead of a hung probe. Two signals, and don't conflate them: `serving` (takeover done) gates `/readyz`; **`healthy`** — a 1 s liveness tick on the *main* runtime (`kaas_observability::record_main_tick`/`main_alive`), reported in `BrokerStatus.healthy` — is what the controller's alive set uses. `serving` can't detect a wedge (a wedged runtime keeps its partitions *open*), which is why `healthy` exists. `alive_brokers()` → `decide_alive()` in `bins/kaas/src/cluster.rs` = connected brokers reporting `healthy` — trusted unconditionally (the old-image `ever_healthy` guard was dropped per the pre-v1 no-backcompat policy). EndpointSlice readiness is now only the no-heartbeats-yet bootstrap fallback. Full write-up: `docs/src/architecture/readiness-rollout.md`. `broker.minReadySeconds` (default 60) stays as belt-and-braces. The PDB is inert for rollouts — StatefulSet updates delete pods directly, not via the eviction API — though it still applies to node drains.

### Broker fencing (gh #249)

Three states, not two: **serving** (EndpointSlice-listed and Ready),
**fenced** (listed, not Ready — exists but isn't serving), **gone** (not
listed). K8s supplies the registry, so a scale-down *is* deregistration —
no `unregister` verb, no tombstones. `BrokerRegistry` keeps not-ready
entries rather than filtering them; an ordinal absent from its **owning
slice** (sharded Services exist) is removed; self is never inserted,
downgraded, or removed by slice data (the gh #208 self-eviction death
spiral). The controller writes the tri-state into `assignment.json`'s
long-dormant `BrokerHealth { Alive, Draining, Dead }`: every *registered*
broker gets a row, and a fenced one keeps the `last_seen` from when it was
last alive.

**The reporting was the motive; the divisor was the bug.** `group_hash`
documents that `hash(groupID) % num_brokers` MUST divide by the full broker
set "including draining / dead", but the list came from `assignment.json`,
which held only the alive set — so losing 1 of 3 brokers silently moved the
divisor 3 → 2 and rehashed ~2/3 of all group and txn coordinators, exactly
when the cluster was already degraded. Don't "clean up" `Dead` rows: they
are the divisor. Test: `a_dead_broker_moves_only_its_own_groups`.

**Draining is fencing from the other side.** SIGTERM calls
`mark_draining()` *before* teardown; the next heartbeat (~1 s) carries it,
the controller drops the broker from the alive set while it is still
healthy enough to hand over, and marks it `Draining` (still registered, so
the divisor holds). The self-pin in `decide_alive` outranks draining — an
empty alive set would unassign the cluster. This is the proactive drain
hint the gh #61/#139 shutdown notes left open.

Fenced is derived from readiness, so a **booting** broker reads as fenced
until takeover completes — deliberate, and what Apache reports for a
registered-but-not-caught-up broker. Readiness still does NOT drive the
alive set (gh #208): that stays on the heartbeat's `healthy` bit, so a
booting broker remains assignable while reading as fenced. Metadata omits
fenced rows; DescribeCluster v2 reports them. Book page:
`docs/src/architecture/broker-fencing.md`.

**Retention IS enforced (gh #250); compaction is not (gh #158).** `bins/kaas` builds a `RetentionCleaner` at boot and sweeps every `KAAS_RETENTION_CHECK_INTERVAL` (default 300 s, Apache's `log.retention.check.interval.ms`; `0` disables). It honours `retention.bytes` **and** `retention.ms`, taking whichever target reaps more, with `-1`/absent meaning retain forever. Policy comes from `TopicConfigPolicySource`, which re-reads `/data/<topic>/.config.json` on every lookup — that re-read *is* the hot-reload path, so a CR edit lands at the next sweep with no restart. The active segment is never reclaimed (that stays `DeleteRecords`' job).

**Three things had to be true together for `retention.ms` to mean anything, and only the third is about retention.** (1) **A topic's `segment.bytes` / `segment.ms` must reach the log.** The engine built one `PartitionConfig` at boot and handed the same copy to every partition, so a topic could ask for 16 MiB segments, have it written to `.config.json` and echoed back by DescribeConfigs, and still roll at the global 1 GiB. `DiskStorageEngine::partition_config_for` now layers the file over the engine default at open, and the sweep re-applies it to live partitions via `Partition::set_config` (an `ArcSwap`, read per append) so `kafka-configs.sh --alter` takes effect without a restart, as in Apache. (2) **`segment.ms` must exist.** Retention only ever deletes *closed* segments, so a topic that never fills a segment keeps everything no matter what its retention says — which is exactly what `kaas-canary-v1` did: 20 MB in 40 h under a 24 h retention, one active segment, nothing to reap. Apache rolls at 7 days by default for this reason; kaas rolled on size only. The age arm lives in the append path and dates a segment by its in-process creation time, falling back to log mtime for one adopted at open. (3) **The enforced default must equal the advertised one.** DescribeConfigs advertised `retention.ms=604800000` as `DEFAULT_CONFIG` while the cleaner treated absent config as retain-forever. Both now read `topic_config_defaults::default_retention_ms()`; `the_enforced_default_is_the_one_describeconfigs_advertises` is the drift guard. **This deletes data that previously accumulated forever** — a topic with no explicit retention now ages out at 7 days, which is what Apache does and what `-1` opts out of.

Two things about that are worth knowing before touching it. **It is leader-gated** via `OwnershipSource` → `Coordinator::owns`: a pass unlinks files on the shared volume, so a non-leader running it is an NFS substrate rule 3 violation and would silly-rename files the real leader holds open (gh #76). The gate degrades to "own everything" with no coordinator (dev/single-broker) and to "own nothing" until the first `assignment.json` load, which delays a sweep rather than skipping it. **And time-based retention dates a segment by its largest record timestamp, falling back to the log file's mtime** — nothing persists a per-segment timestamp (the manifest has no segment list), so `SegmentMeta::max_timestamp` is only populated for segments this process rolled itself; everything inherited across a restart ages by mtime. That is Apache's own fallback (`LogSegment.largestTimestamp` → `lastModified`), not an approximation kaas invented.

The compactor is still absent: `min.compaction.lag.ms` (KIP-58) and `delete.retention.ms` (KIP-354) remain config plumbing only (`topicconfig.rs`, CR → `.config.json` → DescribeConfigs, which advertises a 24 h `delete.retention.ms` default). When compaction lands, tombstone-expiry granularity will be per-batch (Apache is per-record) per the byte-opacity contract.

**The metrics audit did not catch this, and won't catch the next one.** `cleaner_runs` / `cleaner_bytes_reclaimed` sat in `EXPECTED_WIRED` (`crates/kaas-observability/tests/wire_up_audit.rs`) the whole time it was dead code — the audit greps for *call sites*, and `cleaner.rs` had them; nothing checked that anything ever called `cleaner.rs`. A metric can be "wired" and still be structurally unreachable.

### Idempotent producer (gh #12, #22, #30)

The Java producer enables idempotence by default since Kafka 3.0, so every `kafka-console-producer` / `kafka-verifiable-producer` invocation hits this path. Layers of state, all on the shared PVC:

- **InitProducerId handler** (`crates/kaas-broker/src/handlers/init_producer_id.rs`, API key 22, v0–v4). For non-transactional producers (empty `transactional.id`): hands out a fresh PID, epoch=0. For transactional producers: looks up the txn ID in the txn state store and returns the **same PID with epoch+1** on every reconnect — the gh #22 fence-on-rejoin contract.
- **PID allocation** (`crates/kaas-broker/src/producer_id.rs`, gh #219). PIDs must never be reused: the dedupe window below is keyed by `(PID, epoch)`, so a recycled PID lands a fresh producer on a dead producer's sequence history — its batches are then silently dropped as duplicates or rejected with `OUT_OF_ORDER_SEQUENCE_NUMBER`. The pre-gh #219 `AtomicI64::new(1)` reissued PIDs on every restart *and* every broker issued the same ones. Apache uses a quorum-persisted global block allocator; kaas has no quorum (non-goal), so it partitions the space instead: `pid = (broker_id + 1) * 2^40 + local`, with `local` advancing in 1000-PID blocks whose end is persisted to `/data/__cluster/producer_ids/kaas-<id>.json` **before** any PID in the block is handed out (crash → skip forward, never rewind). Each broker is the single writer of its own file — no cross-broker read-modify-write. The `+ 1` keeps broker 0 clear of the legacy low PIDs still sitting in on-disk snapshots.
- **Per-partition sequence tracking** (`crates/kaas-storage/src/idempotence.rs`). Per-PID producer state with a 5-batch ring buffer — mirrors Java's `max.in.flight.requests.per.connection=5`. Classification runs under the partition mutex before append: duplicate (echo cached `baseOffset`, no log write), out-of-order (wire 45), invalid epoch (wire 47), or accept.
- **Snapshot persistence** (`crates/kaas-storage/src/producer_snapshot.rs`). `producer-state.snapshot` next to `manifest.json`; written on take-over and close/relinquish (the same `persist_state_locked` sites as the manifest — not on segment roll); restored on partition open. Without it, broker restart loses the dedupe window and in-flight retries get OUT_OF_ORDER.
- **Txn state store** (`crates/kaas-coordinator/src/txn_state.rs`). Per-`transactional.id` `{PID, epoch, state, partitions, groups, ongoingSinceMs, transactionTimeoutMs}` slot-sharded across `/data/__cluster/txn_state/slot-N.json` (50 slots default, matches Apache's `transaction.state.log.num.partitions=50`). Each broker owns the slots that hash to it under gh #91 routing; on coordinator failover the new owner reads the same slot file off the shared RWX PVC (close-to-open consistency = the file IS the materialised state, no log replay needed). This is the architectural answer to gh #29 — see the "literal `__transaction_state` internal topic" non-goal up top.
- **Cross-partition fence on bump.** Called from the InitProducerId handler after every `epoch > 0` rejoin: walks every partition, advances the PID's epoch and clears the dedupe window, so a zombie batch from the old session is fenced even on partitions the new session hasn't yet touched. gh #108 phase 2 broadcasts fences across brokers via a per-broker fence log under `/data/__cluster/producer_fences/` (`crates/kaas-coordinator/src/fence_log.rs`); peer brokers' `FenceWatcher` (`crates/kaas-broker/src/fence_watcher.rs`) polls and applies.

### Transaction coordinator state machine (gh #23–#28, #37)

Built on top of the txn state store. Handlers in `crates/kaas-broker/src/handlers/`:

- **AddPartitionsToTxn** (key 24, `add_partitions_to_txn.rs`) — `Empty/Complete*` → `Ongoing` stamps `OngoingSinceMs` so the reaper has a deadline clock.
- **AddOffsetsToTxn** (key 25, `add_offsets_to_txn.rs`) — records consumer group IDs that the txn will commit offsets to; same `Ongoing` transition stamps the clock.
- **TxnOffsetCommit** (key 28, `txn_offset_commit.rs`) — stages offsets in a **pending** layer keyed by `(groupID, PID)` in the offset store. They are NOT visible to `OffsetFetch` until commit. Group-coordinator side only (non-coordinators return `NOT_COORDINATOR`).
- **EndTxn** (key 26, `end_txn.rs`) — **two-phase, and the phases are the correctness property (gh #225)**: `prepare → dispatch every marker → complete`. `prepare_end_txn` moves `Ongoing → Prepare{Commit,Abort}` and **deliberately retains `Partitions` and `Groups`** — `Prepare*` plus a retained partition list *is* the durable record of "these markers still owe a write", so a dispatch failure, a coordinator crash, or a producer retry all re-derive the identical dispatch set. `complete_end_txn` is the only thing that clears them and fires the txn offset hook (commit → commit pending; abort → discard pending), and the handler calls it **only once every marker is durable**. Any dispatch failure returns a retriable `COORDINATOR_NOT_AVAILABLE` and leaves the entry prepared. Before gh #225 the store went straight to `Complete*`, cleared the list, then dispatched best-effort — logging and swallowing every failure while still answering `error_code = 0`. That was unrecoverable by construction: the dispatch set was gone, a producer retry was a documented no-op, and no reconcile existed, so a `read_committed` consumer's LSO pinned forever — not just for the lost txn but for every committed record written to that partition after it. Don't re-collapse the phases, and don't let `complete_end_txn` run on a path that hasn't confirmed durability.
- **WriteTxnMarkers** (key 27, `write_txn_markers.rs`) + **marker queue** (gh #175, `crates/kaas-coordinator/src/marker_queue.rs`, `crates/kaas-broker/src/marker_watcher.rs`). Cross-broker COMMIT/ABORT marker dispatch goes through the shared PVC instead of a wire RPC: the txn coordinator writes one JSON file per `(pid, epoch, target_broker)` under `/data/__cluster/marker_queue/to-<target>/`; every broker polls its own `to-<self>/` directory (2 s default) and applies the markers as control-batch appends — same pattern as the fence log. A successful `enqueue` is the **durability boundary** for a peer partition: the entry is on the shared volume and the peer's `MarkerWatcher` retries until it applies (`ApplyOutcome::Retry` keeps the file), so `EndTxn` may complete once the entry is written. An enqueue *failure* is fatal to that attempt — see the gh #225 note on EndTxn above.
- **Timeout reaper + marker reconcile** (started by the broker at boot, same 10 s tick — Apache's `transaction.abort.timed.out.transaction.cleanup.interval.ms` default). The reaper walks slots and transitions overdue `Ongoing` entries to **`PrepareAbort`** (not `CompleteAbort`), bumping the epoch for gh #22 fencing but **keeping `Partitions`/`Groups`** — a timed-out txn owes ABORT markers exactly like a client-driven one. The reconcile (`crates/kaas-broker/src/txn_markers.rs`, `reconcile_pending_markers` over `TxnStateStore::pending_marker_dispatches`) then places those markers and completes the txn, firing the offset hook. **Both halves are needed and neither subsumes the other** (gh #225): the handler's inline dispatch keeps commit latency off the sweep interval, but only the sweep can finish a txn whose producer crashed, was fenced, or never existed — a reaper-aborted txn has no producer to retry at all. Before gh #225 the reaper cleared the partition list with no marker written and `bins/kaas` merely logged a count of the returned `TxnAbortRecord`s (which don't even carry partitions), so every timed-out transaction pinned its partitions' LSO permanently. A dispatch that still fails is left prepared and retried next pass, deliberately unbounded. **Both sweeps are ownership-gated** (`abort_overdue_owned` / `reconcile_pending_markers`'s `owns_txn`, gh #91) on `Broker::owns_txn` — a txn slot file has exactly one legal writer, its coordinator, so the previously ungated sweep had every broker read-modify-writing the same slot on the shared volume (NFS substrate rule 3). The gate degrades in the safe direction at both edges: `owns_txn` answers `true` when no `Coordinator` is installed (dev / single-broker), so nothing stops being swept, and in cluster mode it answers `false` for everything until the first `assignment.json` load, which delays a sweep by one 1 s poll rather than skipping it.

`bins/kaas/tests/eos_v2.rs` exercises the full KIP-447 consume-process-produce-commit round trip against the in-process broker.

### Consumer-group coordinator routing (gh #92)

`coordinator-of-G` is a **pure function**: `hash(groupID) % numBrokers` with the divisor pinned to the full broker set (NOT `len(alive)`), preferred-slot-down falling back to a deterministic alternate from the alive subset. Mirrors Apache Kafka's `partitionFor(groupId)` (which leases the question to `__consumer_offsets` partition leadership); kaas has no `__consumer_offsets` topic, so we hash directly into the broker set. Implementation in `crates/kaas-broker/src/group_hash.rs`.

Group ownership on the broker `Coordinator` is two-tier: explicit `assignment.json.consumerGroups[]` entries win first (the controller's group balancing writes them; this is the forward-compat lever for sticky-rebalance), hash fallback otherwise. The two converge for stable broker sets, so the hash is the load-bearing path in steady state.

**The two tiers can legitimately disagree, and that is why both halves of gh #248 matter.** An explicit entry is sticky across alive-set changes, so it can name a broker the hash no longer would. So (a) `balance_groups` **carries an entry forward while its broker is alive even when the group is absent from `active_groups()`** — that input is the union over *connected* brokers, and a group drops out of it for reasons unrelated to coordination (members all left for a moment, a stale heartbeat window, an in-memory sweep). Retiring on absence handed the group to the hash, which named a different broker: `NOT_COORDINATOR` → `UNKNOWN_MEMBER_ID` → full rebuild, on a healthy group, triggered by an unrelated topic delete. It was not self-healing either — the next recompute's `prev` no longer had the entry — so one missed report moved a coordinator permanently. Retirement is by broker death, not absence. And (b) **anything resolving a group's coordinator must resolve it the same way**: `GroupTakeoverDriver` read the explicit list alone, so a hash-owned group (every brand-new group, and any whose entry was retired) looked unowned and was relinquished on *every* assignment change — dropping the member list, hence `UNKNOWN_MEMBER_ID`, for a move that never happened. Its sweep now runs over `Manager::resident_groups()` (everything in memory) rather than `local_groups()` (already filtered by ownership, so it structurally could not see the groups the sweep existed to drop). Coordinator transitions are logged in both directions — the 2026-08-06 flap was reconstructible only from the client's log.

**The third defect was the one that fired every time, and it was in the mint path.** `balance_groups` created new entries with `rendezvous_pick_group` (highest-random-weight) while brokers resolved the hash tier with `pick_coordinator` (`hash % n` plus a deterministic alternate). Those agree only by coincidence — on the live 3-broker cluster they disagreed for *every* group id tried. So the first entry the controller ever wrote for a group moved it: the group had been served from wherever the fallthrough said, and the entry named somewhere else. One guaranteed `NOT_COORDINATOR` → rebuild per group, shortly after it started, on a healthy cluster. That is why the streams bench passed on 2026-08-05 and failed on 2026-08-06 with an identical build — the move is once-per-group, so whether it costs duplicates depends only on whether it lands before or after the app has committed work. `balance_groups` now mints with `pick_group_coordinator`, so the entry **confirms** where the group already is. It takes `&[BrokerAssignment]` (the rows the writer is about to serialise) rather than a list of alive ids, because `pick_coordinator` divides by the full registered set (gh #249) and anything narrower reintroduces the divisor bug — passing the rows means both sides resolve from byte-identical input. Test: `a_minted_entry_confirms_where_the_hash_already_put_the_group`.

The coordinator manager's group-assignment source is hot-swapped from `bins/kaas/src/cluster.rs` after the broker `Coordinator` boots — the bootstrap source is an always-true local stub used during the brief window before the runtime is up; tests can substitute their own source. **Don't unwire the swap** without re-reading gh #92: an earlier attempt (v0.1.52) hit the chicken-and-egg (strict coordinator checks block fresh-group bootstrap) and was reverted in v0.1.53.

`GroupTakeoverDriver` (`crates/kaas-broker/src/group_takeover.rs`) runs one sweep over every resident group on assignment change (it subsumes the old prev→next diff — a group can only be relinquished if it is resident). The sweep keeps memory bounded across alive-set churn and fixes the gh #89 stale-`--list` symptom. `ListGroups` and `DescribeGroups` filter by coordinator ownership so a stale group entry on a non-coordinator broker isn't visible to clients via the AdminClient's union across brokers.

### Listeners, authentication, authorization (gh #124, #125, #126)

Three orthogonal axes, Strimzi 1:1:

- **`type`**: `internal` (in-cluster only) vs `external` (Gateway + cert-manager + per-broker hostnames). One listener per axis combination is normal — keep `plain` anonymous for in-cluster bench/UI traffic and add an `authed` SCRAM listener side-by-side.
- **`tls`**: `false` / `true`. `mtls` authentication implies `tls: true`; everything else is independent.
- **`authentication.type`**: `none` / `scram-sha-512` / `mtls` / `plain` / `oauth`. Each listener gets its own auth engine selected per listener name (`crates/kaas-auth/src/`). Anonymous listeners use an allow-all engine (no SASL handshake, no principal); authenticated listeners pre-gate connections in `crates/kaas-protocol/src/dispatch.rs` so a client must finish SASL before any non-handshake API is dispatched. **`oauth` = SASL/OAUTHBEARER (gh #42, KIP-255)**: JWTs validated locally against the issuer's JWKS (`crates/kaas-auth/src/oauth.rs`; fetch loop `spawn_jwks_refreshers` in `bins/kaas/src/main.rs`; Strimzi's `KafkaListenerAuthenticationOAuth` field names verbatim through `KAAS_LISTENERS`). Fail-closed before the first JWKS fetch; `alg` allowlist RS256/384/512+ES256; OAUTHBEARER (like PLAIN) refused over non-TLS; mechanism advertisement is per-listener (`AuthEngine::mechanisms`); KIP-368 partial — `maxSecondsWithoutReauthentication` advertises `session_lifetime_ms = min(cfg, token exp)` and the dispatcher answers 58 past the deadline, re-auth must keep the same principal. `KAAS_REQUIRE_SASL` (chart `auth.requireSasl`, gh #251 — re-port of the Go gate, dead config from the cutover until then) hands anonymous listeners the real engine too, so the pre-auth gate arms cluster-wide; `KAAS_AUTH_DISABLED=true` outranks it. SCRAM credentials rotate over the wire via keys 50/51 (KIP-554, gh #252): describe answers from the hot-reloaded credential store, alter derives RFC 5802 keys from the wire's salted material and patches `KafkaUser.spec.authentication.scram` (deletions and SCRAM-SHA-256 are refused with explicit errors — the CR owns the credential lifecycle).

**Authentication is per-listener; authorization is cluster-wide.** That split lives in `crates/kaas-auth/src/`:

- Authorizer — wired via `KAAS_AUTHORIZATION_TYPE` (`""` = none → allow-all; `simple` = ACL-based). `KAAS_SUPER_USERS` (comma-separated `User:foo,User:bar`) wraps the chosen authorizer in a super-user early-allow layer.
- Quota checker — defaults to no-op; switches to real quotas when auth is enabled. Quotas fire **regardless of authorization** — they're orthogonal.

Produce/Fetch handlers route exclusively via the cluster-wide authorizer + quota checker — they don't reach back into the per-listener engine. This is what lets `plain` (anonymous) and `authed` (SCRAM) listeners share the same ACL/quota policy.

**Per-listener Metadata advertisement (gh #125)**: each broker endpoint carries a per-listener port map; the Metadata handler looks up the port matching the request's listener so a client that bootstrapped on :9095 gets back :9095 in the Metadata response, not :9092. Without this, an authed-listener client got routed back to the anonymous listener and looped on SCRAM retry. The listener name on the connection is propagated via `crates/kaas-protocol/src/connstate.rs` (free-form string — no predefined constants; the chart picks the names).

**Quota debt-carry (gh #125)**: the token bucket (`crates/kaas-auth/src/quota.rs`) carries negative balances forward as debt instead of clamping at 0. With clamping, N concurrent clients each saw a "full" bucket and burst at N×rate before throttle kicked in (the 16-vs-10 MiB/s gap observed under bench-perf). Removing the clamp matches KIP-13. Test: `multi_client_contention_carries_debt` in `quota.rs`.

**mTLS principal mapping (gh #43, KIP-371)**: `crates/kaas-auth/src/principal_mapping.rs` parses Apache's `ssl.principal.mapping.rules` syntax — regex against the full subject DN with `$1`/`$2` back-references and optional `/L` / `/U` postfix flags; first matching rule wins, `DEFAULT` returns the CN. Wired on the server (`crates/kaas-protocol/src/server.rs`); the mTLS handshake path applies the mapper to the full subject DN before authenticating. Parse errors bubble at startup so chart-config typos fail fast rather than silently mapping every cert to the CN.

### TopicID propagation (gh #105, KIP-516)

Every `KafkaTopic`'s `Status.TopicID` carries a v4-shape UUID, generated cryptographically in `crates/kaas-operator-controllers/src/kafkatopic_controller.rs` on first reconcile and **never rotated** (Apache's contract: re-created topics get distinct IDs). The *intended* state flow — topic watcher stashes `Status.TopicID` → topic registry surfaces it → Metadata v10+ writes the 16 raw bytes — is only partially wired: the `TopicWatcher` cache (`crates/kaas-k8s/src/topic_watcher.rs`) carries `topic_id`, but the production topic watch (`run_topic_watch` in `kube_watchers.rs`, wired from `bins/kaas/src/main.rs`) inserts registry entries with the all-zero sentinel, so **Metadata currently serves nil topic IDs for every topic** and clients fall back to name-based lookups. Wiring the ID through (and `CreateTopics` v7+ carrying the UUID in its response) is open follow-up.

### Fetch sessions (gh #4)

KIP-227 incremental fetch sessions are stateless: kaas returns **`SessionID=0` on every Fetch response** regardless of what the client sent. Echoing the client's SessionID was the pre-fix bug — clients then sent incremental deltas against state kaas didn't have and silently 'forgot' partitions from their subscription. Apache's documented contract for "broker doesn't support sessions" is `SessionID=0`, which makes clients fall back to full Fetch data per request. CPU cost is fine at kaas's scale; KIP-227 caching is a future optimisation, not a correctness gap.

### KafkaTopic delete on NFS

Deleting a `KafkaTopic` must not leave `.nfsXXXX` silly-renames: NFS renames any unlinked-while-open file into a `.nfsXXXX` entry that EBUSYs the operator's `unlinkat` on the parent directory until every FD closes (gh #76). The production path: the broker's kube topic watch (`run_topic_watch`) sees the K8s `Delete` event → drops the topic from the registry **and calls `engine.abandon_topic(name)`** → fires an assignment recompute (`TopicDeleted`) → the new assignment no longer routes the partitions (the `TakeoverDriver` relinquish is already a no-op for the abandoned ones) → the operator reclaims the directory. A `TopicWatcher` cache with a deletionTimestamp-immediate delete event exists in `crates/kaas-k8s/src/topic_watcher.rs` but is **not wired** into the production pump.

**`abandon_topic` ≠ `relinquish` (gh #219) — don't "unify" them.** Relinquish is a leadership handover: persist manifest + producer snapshot, then close. A delete is not — the topic is gone, the operator reclaims its directory by renaming it aside, and a recreated topic of the same name gets a *fresh* directory at the same path. A `close()` landing after that sequence writes the dead incarnation's HWM and dedupe window into the new incarnation's dir (that is the gh #219 "empty log, HWM == logStartOffset" symptom). So `abandon_topic` closes handles and persists **nothing**, and dropping the in-memory partition forces the next `take_over` to re-open from disk instead of serving the deleted topic's state. Both the delete and the recreate arrive on the same watch stream, so the abandon is ordered before the recreate.

**A deleted topic's committed group offsets go with it (gh #240).** Apache tombstones a topic's entries out of `__consumer_offsets` on delete; kaas keeps offsets in per-group JSON files, so nothing removed them until the same `on_delete` callback started calling `Manager::purge_topic_offsets`. Without it, a delete→recreate under the same name hands the new incarnation the dead one's committed offsets, and if the new log is *shorter* every consumer in the group resumes past its end and idles forever — no error, no log line, on either side. That is what `kafka-streams-application-reset` walks into every run: it *deletes* the Streams internal topics rather than resetting their offsets, precisely because it expects the delete to purge them. Two properties are load-bearing: the purge **filters by coordinator ownership** (the delete event lands on every broker, and a group's offset file has exactly one legal writer — NFS substrate rule 3), and it **unions the on-disk group list with the in-memory one** (`Manager::groups` holds only materialised groups; `OffsetStore::load` would pull a skipped group's stale entries straight back). It rides `on_delete`, which fires for relist retractions too, so a topic deleted while a broker was disconnected is still purged. Related: every write to a group file must go through `OffsetStore::write_group` — the decoder takes the gh #21 v2 envelope only and serde ignores unknown fields, so a stray v1-shaped write decodes back as an *empty* group instead of failing (`delete_partitions` did exactly that until gh #240).

**Topic identity is the CR's `Status.TopicID`, not the directory name (gh #219).** Partition dirs are addressed by name, so a delete→recreate under the same name (Kafka Streams' `application-reset` does this every run) silently inherits the old incarnation's segments, manifest, and — the fatal one — `producer-state.snapshot`, which rejects the new producer's first batch with `OUT_OF_ORDER_SEQUENCE_NUMBER` or swallows it as a duplicate. The `KafkaTopic` reconciler stamps `.topic-id.json` (`crates/kaas-storage/src/topic_identity.rs`) into the topic dir and, on every reconcile, stages the dir aside when the stamp isn't this incarnation's ID. Deliberately reconcile-driven: no delete event, no ordering between watch streams, idempotent. **An unstamped dir is always adopted, never reclaimed** — "unknown identity" must not be destructive, or the first reconcile after upgrade eats every live topic.

**The topic watch is self-restarting and relist-reconciling (gh #202) — don't "simplify" either away.** `run_topic_watch` rebuilds its stream with exponential backoff (1 s → 30 s, reset on any event) instead of returning when the stream ends; it previously returned `Ok(())` on stream end and the caller never restarted it, so one routine relist ended topic tracking for the life of the process and the registry served deleted topics indefinitely. It also diffs each relist (`Event::Init` → `InitApply`* → `InitDone`) against the topics it last reported and retracts the missing ones — a topic deleted while the watch was disconnected never produces a `Delete` event, so the diff is the only way to notice. The tracking set (`TopicWatchState.known`) must outlive individual streams for that to work; a relist interrupted mid-enumeration drops its partial set rather than retracting topics it never saw. `run_topic_watch` now returns `Ok(())` **only** on cancellation.

Reclaim of a deleted topic's directory is two-track and neither track needs a delete event: the reconciler's identity check above handles delete→recreate, and the periodic leader-elected `sweep_topics` pass (`SWEEP_INTERVAL`, 5 min) handles "deleted for good". Both go through `stage_topic_dir` — atomic rename aside to `.deleting-<name>.<nanos>` — so the destructive recurse never runs on a live path a broker may be mid-`Partition::open` on (gh #203), and a staged dir that can't be removed yet is retried next pass rather than aborting it (gh #205).

**Order matters inside that reclaim (gh #220): rename → mkdir the partition dirs → *then* `remove_dir_all` the staged copy.** The rename frees the live path atomically, but the recursive delete after it is a long unlink walk (554 ms measured on NFS), and until the mkdirs land a broker opening a partition on that path gets ENOENT — observed as `create_partition failed` on produce and `take_over failed` on the leader. Don't fold the delete back into `stage_topic_dir`. Belt-and-braces on the other side: `Partition::open` retries its blocking prologue on ENOENT (5 attempts, 750 ms total, `open_blocking_retrying`) — the prologue starts with `mkdir_all`, so an ENOENT after it can only mean someone is re-creating the path, never that the path is wrong.

**The broker must not open a topic dir the operator hasn't reclaimed (gh #241).** gh #220 covers the broker that is *about* to open; the other half is the broker that already **has** it open when the reclaim renames it aside. FDs follow the renamed inode, so every subsequent append lands in the `.deleting-*` copy while the live path serves an empty log — silently: no error to the producer, none to the consumer, nothing in the broker log, and ListOffsets still answers from in-memory state, so the partition advertises records Fetch cannot return until the staged copy is deleted and they are gone for good. The cure is ordering, not detection: `DiskStorageEngine::ensure_open` consults a `TopicIdentityResolver` (the `TopicRegistry`, fed `status.topicId` by the topic watch) and refuses with `StorageError::StaleTopicDir` — retriable, mapped to `LEADER_NOT_AVAILABLE` — when the dir carries someone else's stamp. The gh #215 reconcile re-drives take-over until the operator's reclaim lands. **The incarnation is three-valued and all three arms are load-bearing**: `Unknown` (no CR seen — unreachable API server, `KAAS_TOPICS` seeding, dev mode) **adopts**, because brokers serving existing topics without the operator outranks this check; `Pending` **waits** over a stamped dir — and `Pending` covers two states, both load-bearing: a CR seen but not yet stamped, *and* a topic absent from a registry whose watch has already completed a full list. The second is the one that actually fires in production: a broker learns it leads a partition from `assignment.json` (1 s poll), which routinely beats its own CR watch, so a freshly (re)created topic is momentarily absent from the registry — treating that as `Unknown` let the gate adopt the stale dir and the bug survived the first fix attempt. `TopicRegistry::mark_synced` (fired from the watch's first `InitDone`) is what separates "haven't looked yet" from "looked, not ours yet"; it latches and is never cleared. `Known` compares. An *unstamped* dir is always adopted, mirroring the operator's own never-destructive-on-unknown rule. The registry keeps the id in a side map on purpose — filling in `TopicMeta.topic_id` would flip Metadata from advertising nil topic IDs to real ones, which is gh #105's call. Residual window: a broker that opened a stale dir under `Unknown` (API server unreachable for the broker but not the operator) is still exposed.

### Storage layout

Everything cluster-wide lives in the **cluster-state dir** — `KAAS_CLUSTER_DIR`, default `<data_dir>/__cluster`; the chart's `storage.controlPlane.enabled` mounts it on its own PVC (gh #221 phase 1) so a full data volume can't take the control plane down: `assignment.json` (controller-written, broker-read), `acls.json`, `credentials.json` (operator-written, broker-read with hot-reload), `txn_state/slot-*.json` (gh #22 + #28 — txn coordinator state, slot-sharded; replaces Apache's `__transaction_state` internal topic, see the non-goal up top), `producer_fences/from-kaas-*.json` (gh #108 phase 2 cross-broker producer-epoch fence broadcast), `producer_ids/kaas-<id>.json` (gh #219 per-broker PID block high-water; each broker writes only its own), `marker_queue/to-<broker>/` (gh #175 cross-broker txn marker dispatch), and per-group offset files under `__consumer_offsets/<groupID>.json` (moved under `__cluster/` by gh #223 — at the data-dir root the operator's orphan sweep deleted them every pass; the legacy-dir adoption shim was dropped per the pre-v1 no-backcompat policy). The `kaas-controller` Lease lives in K8s (not on the PVC).

**Volume pool (gh #221 phase 2).** `storage.pool[]` in the chart declares additional named RWX volumes ("log dirs", KIP-113 vocabulary), mounted at `/vols/<name>` and advertised via `KAAS_LOG_DIRS` (broker + operator). `KafkaTopic.spec.storage.volumes` binds a topic to an eligible set; the reconciler round-robins new partitions over it and records placement in `status.volumeAssignments` (creation-sticky — spec edits never move data; drift surfaces as `status.partitionsOutsideSpec`). The broker's topic watch stashes assignments into the `TopicRegistry`, which implements the engine's `PlacementResolver`; unknown/unplaced always falls back to the default data dir. **Where the data actually is outranks the placement record (gh #234).** Placement is eventually-consistent — partitions are routinely opened before `status.volumeAssignments` is written — so `partition_dir` resolves: assigned root if it holds a `manifest.json`; else any known root that does (loud WARN, no data movement); else the assigned root (fresh create). Pre-fix, a restart re-derived the assigned root, found it empty, and half the topic silently came up as fresh 0-byte logs. Only the explicit migration path (`move_partition_to_log_dir`) relocates bytes. gh #224 adds `spec.storage.volumeSelector` (label-match over `storage.pool[].labels`, mutually exclusive with `volumes`) and the `kaas.rs/migrate-to-volume` annotation (level-triggered broker-side drain driver over the AlterReplicaLogDirs path). Topic-level files and the gh #219 identity check are per involved root; the orphan sweep walks every pool root. Book page: `docs/src/architecture/volume-pool.md`.

Per-topic files live at `/data/<topic>/`: `.config.json` (retention/segment/compaction knobs) and `.topic-id.json` (gh #219 incarnation stamp — see "KafkaTopic delete on NFS"). Per-partition data lives at `/data/<topic>/<partition>/` with epoch-prefixed segment filenames so a stale leader's late writes can't corrupt a new leader's log. Sibling files: `manifest.json` (epoch + HWM + logStartOffset), `producer-state.snapshot` (gh #12 idempotent-producer dedupe window — see "Idempotent producer" above), and `txn-index.snapshot` (gh #177 read_committed indexes: open-txn first offsets → LSO, aborted list → `AbortedTransactions[]`; same persist triggers and superseded-epoch guard as the producer snapshot, restored on open with aborted entries below logStart evicted).

### Helm chart & deployment

`deploy/helm/kaas/` is the source of truth for production config (replicas, controller-Lease tuning, storage class, image repos). The chart bundles its CRDs in `crds/` (auto-generated by `cargo xtask gen-crds`). Helm intentionally does not upgrade CRDs across releases — see the chart's `README.md` for the upgrade procedure.

**Listeners are a Strimzi-shape array (gh #126).** `.Values.listeners` is `[]listener` where each entry has its own `name` (free-form), `port`, `type` (`internal` / `external`), `tls`, `authentication.type`, and an optional `enabled` flag (absence = enabled — only `external` and `authed` ship as `enabled: false` defaults). Templates iterate this array to emit (a) the StatefulSet containerPorts + `KAAS_LISTENERS` JSON env, (b) headless + ClusterIP Service ports, (c) the NOTES.txt bootstrap-host output. Helpers in `_helpers.tpl`: `kaas.listenersJSON`, `kaas.findListener`, `kaas.firstByType`, `kaas.hasEnabledExternalListener`, `kaas.superUsersList`. **The KafkaCluster CR template still synthesizes the legacy single-listener shape** via `kaas.firstByType` for backwards-compat with the operator — a follow-up will refactor the operator side to consume the array natively.

Cluster-wide authorization lives at `.Values.authorization.{type,superUsers}` (top-level, not nested under any listener). `type: ""` (default) leaves authorization off; `type: simple` enables ACL enforcement. `superUsers` (list of `User:foo` strings) is emitted as `KAAS_SUPER_USERS` and wraps whatever authorizer the broker picked in the super-user early-allow layer.

**Storage substrate**: the chart accepts `storage.accessMode: ReadWriteOnce` + a local-path class for single-broker deployments (the k3s overlay does this — RWX-NFS was the source of perf-bench DeadlineExceeded errors during saturation tests). Multi-broker requires `ReadWriteMany` with NFSv4-class semantics (same-directory rename atomicity, fsync durability, close-to-open consistency); see NOTES.txt for the provider matrix.
