# Topic delete & recreate

What has to happen, and in what order, when a `KafkaTopic` is deleted and possibly recreated under the same name: the rules that keep one incarnation's state out of the next.

This spans the topic watch (`crates/kaas-k8s`), the broker and engine (`crates/kaas-broker`, `crates/kaas-storage`), the offset purge (`crates/kaas-coordinator`) and the reclaim (`crates/kaas-operator-controllers`). The design is explained in [File-handle ownership](../architecture/file-handles.md#topic-delete-the-handle-close-path), [The RWX substrate contract](../architecture/nfs-substrate.md#names-are-not-identities) and [Consumer-group coordination](../architecture/consumer-groups.md#writing-offsets). This page holds the rules for changing that code.

Deleting a `KafkaTopic` must not leave `.nfsXXXX` silly-renames: NFS renames any unlinked-while-open file into a `.nfsXXXX` entry that EBUSYs the operator's `unlinkat` on the parent directory until every FD closes (gh #76). The production path: the broker's kube topic watch (`run_topic_watch`) sees the K8s `Delete` event → drops the topic from the registry **and calls `engine.abandon_topic(name)`** → fires an assignment recompute (`TopicDeleted`) → the new assignment no longer routes the partitions (the `TakeoverDriver` relinquish is already a no-op for the abandoned ones) → the operator reclaims the directory.

**`abandon_topic` ≠ `relinquish` (gh #219) — don't "unify" them.** Relinquish is a leadership handover: persist manifest + producer snapshot, then close. A delete is not — the topic is gone, the operator reclaims its directory by renaming it aside, and a recreated topic of the same name gets a *fresh* directory at the same path. A `close()` landing after that sequence writes the dead incarnation's HWM and dedupe window into the new incarnation's dir (that is the gh #219 "empty log, HWM == logStartOffset" symptom). So `abandon_topic` closes handles and persists **nothing**, and dropping the in-memory partition forces the next `take_over` to re-open from disk instead of serving the deleted topic's state. Both the delete and the recreate arrive on the same watch stream, and the watch awaits the delete callback (gh #331), so the abandon is ordered before the recreate.

**A deleted topic's committed group offsets go with it (gh #240).** Apache tombstones a topic's entries out of `__consumer_offsets` on delete; kaas keeps offsets in per-group JSON files, so nothing removed them until the same `on_delete` callback started calling `Manager::purge_topic_offsets`. Without it, a delete→recreate under the same name hands the new incarnation the dead one's committed offsets, and if the new log is *shorter* every consumer in the group resumes past its end and idles forever — no error, no log line, on either side. That is what `kafka-streams-application-reset` walks into every run: it *deletes* the Streams internal topics rather than resetting their offsets, precisely because it expects the delete to purge them. Two properties are load-bearing: the purge **filters by coordinator ownership** (the delete event lands on every broker, and a group's offset file has exactly one legal writer — NFS substrate rule 3), and it **unions the on-disk group list with the in-memory one** (`Manager::groups` holds only materialised groups; `OffsetStore::load` would pull a skipped group's stale entries straight back). It rides `on_delete`, which fires for relist retractions too, so a topic deleted while a broker was disconnected is still purged. **The watch awaits that callback (gh #331).** As a detached spawn, a recreate could be applied mid-purge, and the purge then erased the new incarnation's commits: the consumer read -1 and reset, with no error on either side. Now the registry doesn't know the topic until the purge is done, so a commit answers 3, which clients retry. The cost is that a slow purge holds up the watch's other topic events for as long as it runs. **A commit asks again under the group's write lock (gh #335)**, via `OffsetStore::set_partition_source`: the handler's known-topic check is outside it, so a commit queued behind the purge used to write an offset for a topic that was gone. The registry removal comes before the purge, so one that sees the topic has the lock first and gets purged, and one that gets the lock later sees it gone, unless the recreate has been applied by then: a commit that waits out a delete *and* a recreate still writes the dead incarnation's offset, and one refused just before a recreate answers 0 for what it didn't store. The watch holds the recreate until the purge has finished every group, so that takes a very long wait. Closing it needs offsets that know their topic's incarnation (gh #346). Staged transactional offsets go with the purge too, as in Apache's `GroupMetadata.removeOffsets`. **The offset cache only moves after the write lands (gh #318)**: `write_and_cache` holds a per-group striped lock across read cache → write file → update cache, because concurrent commits would otherwise merge from the same old cache and drop each other's offsets. So a failed commit or delete leaves fetches answering what's on disk, and the retry finds the group as it was. A file that can't be *read* isn't "no offsets": `Manager::group_load_error` answers 14 for OffsetFetch, DescribeGroups and DeleteGroups (gh #326), because a consumer told -1 resets per `auto.offset.reset`. Related: every write to a group file must go through `OffsetStore::write_group` — the decoder takes the gh #21 v2 envelope only and serde ignores unknown fields, so a stray v1-shaped write decodes back as an *empty* group instead of failing (`delete_partitions` did exactly that until gh #240).

**Topic identity is the CR's `Status.TopicID`, not the directory name (gh #219).** Partition dirs are addressed by name, so a delete→recreate under the same name (Kafka Streams' `application-reset` does this every run) silently inherits the old incarnation's segments, manifest, and — the fatal one — `producer-state.snapshot`, which rejects the new producer's first batch with `OUT_OF_ORDER_SEQUENCE_NUMBER` or swallows it as a duplicate. The `KafkaTopic` reconciler stamps `.topic-id.json` (`crates/kaas-storage/src/topic_identity.rs`) into the topic dir and, on every reconcile, stages the dir aside when the stamp isn't this incarnation's ID. Deliberately reconcile-driven: no delete event, no ordering between watch streams, idempotent. **An unstamped dir is always adopted, never reclaimed** — "unknown identity" must not be destructive, or the first reconcile after upgrade eats every live topic.

**The topic watch is self-restarting and relist-reconciling (gh #202) — don't "simplify" either away.** `run_topic_watch` rebuilds its stream with exponential backoff (1 s → 30 s, reset on any event) instead of returning when the stream ends; it previously returned `Ok(())` on stream end and the caller never restarted it, so one routine relist ended topic tracking for the life of the process and the registry served deleted topics indefinitely. It also diffs each relist (`Event::Init` → `InitApply`* → `InitDone`) against the topics it last reported and retracts the missing ones — a topic deleted while the watch was disconnected never produces a `Delete` event, so the diff is the only way to notice. The tracking set (`TopicWatchState.known`) must outlive individual streams for that to work; a relist interrupted mid-enumeration drops its partial set rather than retracting topics it never saw. `run_topic_watch` now returns `Ok(())` **only** on cancellation.

Reclaim of a deleted topic's directory is two-track and neither track needs a delete event: the reconciler's identity check above handles delete→recreate, and the periodic leader-elected `sweep_topics` pass (`SWEEP_INTERVAL`, 5 min) handles "deleted for good". Both go through `stage_topic_dir` — atomic rename aside to `.deleting-<name>.<nanos>` — so the destructive recurse never runs on a live path a broker may be mid-`Partition::open` on (gh #203), and a staged dir that can't be removed yet is retried next pass rather than aborting it (gh #205).

**Order matters inside that reclaim (gh #220): rename → mkdir the partition dirs → *then* `remove_dir_all` the staged copy.** The rename frees the live path atomically, but the recursive delete after it is a long unlink walk (554 ms measured on NFS), and until the mkdirs land a broker opening a partition on that path gets ENOENT — observed as `create_partition failed` on produce and `take_over failed` on the leader. Don't fold the delete back into `stage_topic_dir`. Belt-and-braces on the other side: `Partition::open` retries its blocking prologue on ENOENT (5 attempts, 750 ms total, `open_blocking_retrying`) — the prologue starts with `mkdir_all`, so an ENOENT after it can only mean someone is re-creating the path, never that the path is wrong.

**The broker must not open a topic dir the operator hasn't reclaimed (gh #241).** gh #220 covers the broker that is *about* to open; the other half is the broker that already **has** it open when the reclaim renames it aside. FDs follow the renamed inode, so every subsequent append lands in the `.deleting-*` copy while the live path serves an empty log — silently: no error to the producer, none to the consumer, nothing in the broker log, and ListOffsets still answers from in-memory state, so the partition advertises records Fetch cannot return until the staged copy is deleted and they are gone for good. The cure is ordering, not detection: `DiskStorageEngine::ensure_open` consults a `TopicIdentityResolver` (the `TopicRegistry`, fed `status.topicId` by the topic watch) and refuses with `StorageError::StaleTopicDir` — retriable, mapped to `LEADER_NOT_AVAILABLE` — when the dir carries someone else's stamp. The gh #215 reconcile re-drives take-over until the operator's reclaim lands. **The incarnation is three-valued and all three arms are load-bearing**: `Unknown` (no CR seen — unreachable API server, `KAAS_TOPICS` seeding, dev mode) **adopts**, because brokers serving existing topics without the operator outranks this check; `Pending` **waits** over a stamped dir — and `Pending` covers two states, both load-bearing: a CR seen but not yet stamped, *and* a topic absent from a registry whose watch has already completed a full list. The second is the one that actually fires in production: a broker learns it leads a partition from `assignment.json` (1 s poll), which routinely beats its own CR watch, so a freshly (re)created topic is momentarily absent from the registry — treating that as `Unknown` let the gate adopt the stale dir and the bug survived the first fix attempt. `TopicRegistry::mark_synced` (fired from the watch's first `InitDone`) is what separates "haven't looked yet" from "looked, not ours yet"; it latches and is never cleared. `Known` compares. An *unstamped* dir is always adopted, mirroring the operator's own never-destructive-on-unknown rule. The registry keeps the id in a side map on purpose — filling in `TopicMeta.topic_id` would flip Metadata from advertising nil topic IDs to real ones, which is gh #346's call. Residual window: a broker that opened a stale dir under `Unknown` (API server unreachable for the broker but not the operator) is still exposed.
