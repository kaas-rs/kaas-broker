# KIP-890 — Transaction verification (part 1)

**Status: implemented (part 1)** — see the [KIP index](../kip-index.md). Part 2
is past the parity target.

## What the KIP changes in Apache Kafka

A transaction's markers only go to the partitions its coordinator knows about.
So a batch that lands on a partition outside that set opens a transaction no
marker will ever close. It needs no malice, only a retry delayed past an abort.
The partition's last stable offset stays pinned at that batch, and every
`read_committed` consumer stops there for good.

Part 1 (on by default in 3.7, through
`transaction.partition.verification.enable`) makes a partition leader ask the
coordinator before a transaction's first batch lands on it.

## kaas's implementation

The rules are Apache's (`TransactionCoordinator.handleVerifyPartitionsInTransaction`,
`ReplicaManager`, `UnifiedLog.analyzeAndValidateProducerState`, branch 3.7). What
a client's transactional batch with a producer id gets:

| Situation | Answer |
|---|---|
| The producer already has an open transaction on this partition | appended, nothing asked |
| The partition is in the producer's ongoing transaction | appended |
| Unknown transactional id, or another producer's id | `INVALID_PRODUCER_ID_MAPPING` (49) |
| An earlier producer epoch | `INVALID_PRODUCER_EPOCH` (47) |
| The partition isn't in the transaction, or none is ongoing | `INVALID_TXN_STATE` (48) |
| The transaction is being ended, or the slot can't be read | `NOT_ENOUGH_REPLICAS` (19), retried |
| A marker overtook the coordinator's answer | `INVALID_TXN_STATE` (48) |

Two differences, neither visible to a client:

- **No RPC.** Apache's leader sends `AddPartitionsToTxn` v4 to the coordinator.
  kaas's reads the coordinator's slot file off the shared volume. The coordinator
  writes it before answering the client's `AddPartitionsToTxn`, and close-to-open
  consistency makes that visible to any broker.
- **No switch.** `transaction.partition.verification.enable` has no equivalent,
  because kaas has no broker-config surface for it and no client needs it off.

The race the KIP's guard exists for is closed the same way. The coordinator's
yes can be overtaken by a marker, so the leader issues a token first and checks
it under the partition lock when appending. Any append from that producer clears
it, including the marker. Tokens are unique, so an old answer can't match a later
verification for the same producer.

The check costs one slot read per transaction per partition. It runs on the
blocking pool and takes no lock, since a slot is replaced atomically. After a
crash the open transactions come back from a replay of the log, so an ongoing
transaction doesn't start verifying again
([storage hot path](../../architecture/storage-hot-path.md)).

One limit: this stops a transaction from starting to hang, and doesn't clear one
that already does from an earlier release. Nothing sends a marker for it.

## How it's verified

- `a_batch_outside_its_transaction_gets_apaches_codes` in
  `crates/kaas-broker/src/handlers/produce.rs` pins each code.
- `a_delayed_retry_cant_pin_the_last_stable_offset`, in the same file, runs the
  delayed retry on the disk engine and through a restart.
- `a_verification_a_marker_overtook_is_refused` and
  `a_stale_verification_doesnt_pass_for_the_next_one` in
  `crates/kaas-storage/src/partition.rs` pin the race.
- `verify_partition_reads_another_brokers_slot` in
  `crates/kaas-coordinator/src/txn_state.rs` pins the cross-broker read.
- `verifying_a_transactional_batch_doesnt_wait_on_the_store` in
  `crates/kaas-broker/tests/coordinator_io_off_workers.rs` pins the lock-free read.
