## Storage hot path & file-handle ownership

The broker's storage engine is heavily optimised for shared-NFS substrates where every NFS COMMIT round-trip is the dominant cost. The Produce path (gh #80/#81/#82) issues **one NFS COMMIT per group of concurrent batches**, not per record — a per-partition committer task drains flush requests and runs one log `sync_all()` per cycle while concurrent appenders await a condvar. The index file is **not** fsynced on the hot path (rebuildable on takeover); the manifest is **not** rewritten per Produce — it's persisted only on partition open (takeover routes through open), on close/relinquish, and when DeleteRecords or retention advances the log start (durable before the answer and before any file goes, gh #311), so its `HighWatermark` can lag in-memory state. **The one exception to that order is a full volume**: the manifest's tmp+rename needs a free block, so on ENOSPC the covered segments go first, or neither DeleteRecords nor retention could ever free the volume. `Partition::open` makes that safe by clamping log start to the first segment's base, as Apache's `LogLoader` does. A target inside the active segment syncs the log first, so a durable log start can't pass the durable log end. If that sync can't run because the partition is stalled, the closed segments covered still go and the answer is `Stalled` (gh #325): freeing space is how an ENOSPC stall ends. A log that ends below log start anyway restarts at log start at open, as in Apache's `LogLoader`, so the next append is readable. Segment recovery runs at takeover time and reconciles. **Recovery is bounded by a recovery checkpoint** (Kafka's recovery-point, per partition; `crates/kaas-storage/src/recovery_checkpoint.rs`): `recovery-checkpoint.json` records `{segment_base, byte_pos, last_batch_pos, last_batch_crc}` — the committer writes it once the fsynced log grows `CHECKPOINT_INTERVAL_BYTES` (64 MiB) past the last one (that position counts bytes in the *active* segment, so every roll resets it — the size roll didn't until the gh #230 verification, which silently stopped mid-segment checkpoints after the first roll), and a clean close/relinquish writes it at EOF. `Partition::open` resumes the HWM scan *on* the batch at `last_batch_pos` (`scan_high_watermark_from`) instead of byte 0 when the checkpoint names the current active segment and the batch there carries `last_batch_crc`, and accepts the result only if that scan parses cleanly at least to `byte_pos` (the CRC binding is what stops a batch-shaped record payload from passing as a boundary); otherwise (missing/stale/rolled/truncated/off a batch boundary) it falls back to a full scan — always correct, cheap with a bounded `segment.bytes`. Net: a graceful restart re-reads one batch (checkpoint at EOF), a crash re-scans ≤64 MiB. **The checkpoint carries no offsets (gh #230)** — the HWM always comes from batch headers on disk, so a wrong checkpoint costs a full scan, never offsets. Until gh #230 it seeded the HWM, and a stale one that named this segment's base but landed mid-batch also made the scan "prove" garbage at its position, so the torn-tail truncation below cut real batches off the log. Don't reintroduce a trusted offset in it.

**The recovery scan verifies CRCs and truncates the torn tail (gh #228, gh #226).** `scan_high_watermark_from` returns a `ScanResult { high_watermark, valid_end, stop }`. It validates each batch against its own v2 CRC32C (field at batch byte 17..21, covering byte 21 onward — no record contents are read, so byte-opacity holds) and stops at the first batch that is short, structurally impossible, or fails its checksum. `Partition::open` then truncates the active log to `valid_end` **before any write handle is used**, and — the load-bearing half — resets `ActiveSegment::log_size` to it. Without that reset appends resume at the file's `stat()` length, i.e. *past* the garbage, so the log becomes `[valid][torn][new]`; the next recovery stops at the tear and every record written after it is gone, having been acked and (at `flushIntervalMessages: 1`) fsynced, with its offsets re-issued to different data. Two invariants: truncation only ever removes bytes the scan **proved** unparseable (a clean log is never touched, so a spurious size discrepancy can't destroy data), and it is bounded by the checkpoint — corruption *before* `last_batch_pos` is trusted, not detected, while a checkpoint that fails verification never bounds anything (the full scan runs instead). `Fs::truncate` defaults to `Unsupported` so wrapper/fake filesystems don't silently claim success; recovery stays correct there because the `log_size` reset still happens. The `KAAS_FLUSH_INTERVAL_MESSAGES` env var (default 1 = honest acks=all) is the durability/throughput dial — mirrors Apache Kafka's `log.flush.interval.messages`. Core modules: `crates/kaas-storage/src/{engine,disk,partition,segment,manifest,recovery_checkpoint}.rs`.

Segment roll splits the work: the in-memory swap (log fsync + create new active + pointer swap) runs under the partition mutex; the deferred finalize (index fsync, close old FDs) runs in a spawned task. `DeleteRecords` (API key 21) drives `logStart` advance and unlinks fully-covered *closed* segments; the active segment is never reclaimed.

**Only the partition's current leader holds open log/index file descriptors** (gh #76 follow-up). `Partition::open` opens only the active segment's handles; closed segments stay metadata-only. `TakeoverDriver` calls the engine's take-over which opens handles before recovery; relinquish closes them. This makes leader-side file removal (segment retention, DeleteRecords, segment roll cleanup) actually free disk on NFS rather than silly-renaming the file because peer brokers held it open. The committer re-locks the partition mutex inside `spawn_blocking` and fsyncs while holding it (readers stay unaffected via the ArcSwap snapshot). Syncing a cloned FD outside the lock was built and measured under gh #232 and then **reverted** — it worked mechanically (writes grew +2.9%) but produced no throughput, and it is not worth the durability-critical subtlety it introduced: the published flush seq had to be the one sampled *before* the sync, an invariant no test covered and that a tidying refactor would naturally break, silently acking data as durable that may not be on disk. Don't rebuild it without first re-reading the budget below.

**A failed log fsync must stall the partition wherever it happens (gh #289).** Linux reports a writeback error once per file descriptor and can mark the failed pages clean, so the next fsync on that FD succeeds without them reaching the disk. Both roll paths sync the FD the committer syncs, so an error swallowed there would let the committer's next success ack an appender whose bytes never landed. Every sync of the active log on a partition that keeps serving goes through `PartitionInner::mark_flush_failed` (`close()` ignores its sync error, safely: it drops the handles straight after, so no later sync can succeed on that FD), and `await_flush` refuses any seq at or below `failed_flush_seq`, even after the re-arm has moved `completed_flush_seq` past it.

**Takeover raises the epoch and rolls a fresh segment — both halves are load-bearing (gh #227).** `Partition::take_over(epoch)` sets `guard.epoch = epoch`, rolls the active segment to a new epoch-stamped file, and persists the manifest *before* the partition accepts a write. Until gh #227 the engine's `take_over` discarded its `epoch` argument and nothing else advanced the epoch, so the append fence compared against 0 and passed everything, every segment carried the same epoch, and a new leader appended to the file the outgoing one still had open — two `write_at` calls at independent `log_size` values interleaving in one log. The window is not just broker death: any partition move takes leadership off a perfectly healthy broker, which keeps acking until its own `assignment.json` watch catches up. gh #206 made those moves rare (the balancer no longer reshuffles unrelated topics on every topic create/delete) but not impossible, so the fence is still what makes them safe. Three invariants to preserve: take-over is **idempotent at or below the current epoch** (`on_change` and the gh #215 reconcile both re-drive it); a roll over an *empty* active segment lands at the same base offset, so `list_segments` keeps only the highest epoch per base offset; and `persist_state_locked` **re-reads the on-disk manifest and writes nothing if its epoch is higher** — otherwise a fenced leader's relinquish rolls the epoch back and republishes its stale HWM over its successor's. `close()` skips the recovery checkpoint on that path too: the directory is the successor's. **The gh #215 reconcile compares epochs, not just the open set** — because `take_over` now does work *after* the open, a failed roll/persist leaves a partition that is open (so the old open-set-only check called it converged) but still at the previous leader's epoch with the fence unarmed, and nothing re-drove it until the next assignment change. `StorageEngine::partition_epoch` answers "open at the right epoch"; an engine returning `None` (memory/dev) keeps the open-set-only semantics. **That reported epoch must stay durable-only**: `take_over` raises `guard.epoch` before the persist (the persist writes it) and puts it back if the write fails, because a raised-but-unsaved epoch reports a takeover that never finished as complete and the reconcile then skips it forever. A re-drive rolls again at the same epoch over the segment the failed attempt created, so the roll skips its outgoing-file removal when the new path is the one it already occupies. **All manifest writes go through `manifest::write_unless_superseded`** (gh #235): the epoch is the durable fence seed and no writer may lower it. Every writer reads, works, then writes back, and `Partition::open`'s gap spans a whole recovery scan — a takeover completing in it used to get replayed over, silently unarming the fence with no error and no way for the reconcile to notice (the winner's in-memory epoch stayed correct, so the partition looked converged). `open` adopts the returned epoch rather than serving below the durable one. Re-reading cannot close the window — NFS has no compare-and-swap — but identical writes are skipped outright, so a steady-state open touches the manifest not at all.

**The stale-leader ack window is bounded, not zero (gh #164).** A deposed-but-alive leader keeps accepting `acks=all` writes until its own `assignment.json` poll lands — up to ~1 s plus the NFS attribute-cache TTL, capped at 3 s by the self-fence *only* when the reassignment was caused by lost controller connectivity (a balancer-driven move off a healthy broker never trips the self-fence). During that window an acked batch lands in the old-epoch segment at offsets the new leader re-issues: the gh #227 fence guarantees the new incarnation's log is never corrupted by it, but the acked write is lost. There is no synchronous producer-side fence to close this — Apache's Produce request carries no `currentLeaderEpoch` at any version (KIP-320's field is Fetch/ListOffsets-side; the record-batch header's `partitionLeaderEpoch` arrives as -1 and is broker-stamped in Apache), so inventing one would break parity, and Apache's own equivalent window is closed by replication, a kaas non-goal. Closing it would take event-driven assignment delivery or a durable-epoch check on first write after takeover — file a scoped issue before attempting either.

**Why it was reverted, and what actually binds.**

**On a slow-fsync substrate the produce ceiling is set by how many durable writes are in flight, and almost nothing in the broker moves that number.** Throughput obeys Little's law: `concurrent writes × bytes per write ÷ write RTT`. Measured on this NAS: `4.8 × 49,617 B ÷ 16.64 ms = 14.4 MB/s`, against 14.42 MB/s actually observed — the model is exact, and at a single broker the concurrency term sat at ~5 no matter what was changed (all the measurements below are single-broker). Levers tested, all flat: broker CPU 2 → 6 cores (+0.5%), the partition mutex (gh #232, +2.9% write size, no throughput), partition count 16 → 64 (flat, and clearly worse on tail latency — it trades bytes-per-round-trip against number-of-round-trips), and client `max.in.flight.requests.per.connection` 5 → 20 with `enable.idempotence=false` (14.40 → 14.42 MB/s, i.e. nothing). The NFS transport is not the limit either: `bklog_u` is 0 cumulatively, so RPCs never wait for a slot, and the link runs at ~14% utilisation. Only `KAAS_FLUSH_INTERVAL_MESSAGES` moves the number (3.21×), and it does so by *skipping* the durability wait — see gh #212. **So the levers are lower fsync latency (faster storage) or fewer/larger writes — not broker restructuring, not more client concurrency, not more partitions.** **Broker count is the one lever that does move it, and the mechanism is not understood.** Three brokers reproducibly deliver ~1.58x a single broker — 23.13 / 23.25 MB/s across two runs on different builds versus 14.4-15.1 MB/s across four single-broker runs, both clusters tight. That is not explained by any of the above: all three broker pods share one node, hence one kernel NFS client and one transport, and raising a single broker's CPU or the client's in-flight window changed nothing. Treat multi-broker as the representative configuration for perf work, and treat the 3-vs-1 mechanism as an open question rather than assuming it is partition-leadership spread. Before optimising this path again, compute the Little's-law budget from `mountstats` (`WRITE` ops / bytes_sent / rtt on the data mount) and check which term you are actually moving.

## Retention and compaction

**Retention IS enforced (gh #250); compaction is not (gh #158).** `bins/kaas` builds a `RetentionCleaner` at boot and sweeps every `KAAS_RETENTION_CHECK_INTERVAL` (default 300 s, Apache's `log.retention.check.interval.ms`; `0` disables, though the chart can't set `0` yet, gh #342). It honours `retention.bytes` **and** `retention.ms`, taking whichever target reaps more, with an explicit `-1` meaning retain forever and absent taking the 7-day default. Policy comes from `TopicConfigPolicySource`, which re-reads `/data/<topic>/.config.json` on every lookup — that re-read *is* the hot-reload path, so a CR edit lands at the next sweep with no restart. The active segment is never reclaimed (that stays `DeleteRecords`' job). **Retention only runs when `cleanup.policy` includes `delete` (gh #339)**, through `TopicConfigFile::allows_delete`, which `DeleteRecords` shares: with no compactor, a `compact` topic keeps every record and its disk use only grows. **An unreadable `.config.json` deletes nothing for that pass**: the 7-day default is the unsafe answer when the topic might be `compact` or `retention.ms=-1`. An absent file is still the default.

**Three things had to be true together for `retention.ms` to mean anything, and only the third is about retention.** (1) **A topic's `segment.bytes` / `segment.ms` must reach the log.** The engine built one `PartitionConfig` at boot and handed the same copy to every partition, so a topic could ask for 16 MiB segments, have it written to `.config.json` and echoed back by DescribeConfigs, and still roll at the global 1 GiB. `DiskStorageEngine::partition_config_for` now layers the file over the engine default at open, and the sweep re-applies it to live partitions via `Partition::set_config` (an `ArcSwap`, read per append) so `kafka-configs.sh --alter` takes effect without a restart, as in Apache. (2) **`segment.ms` must exist.** Retention only ever deletes *closed* segments, so a topic that never fills a segment keeps everything no matter what its retention says — which is exactly what `kaas-canary-v1` did: 20 MB in 40 h under a 24 h retention, one active segment, nothing to reap. Apache rolls at 7 days by default for this reason; kaas rolled on size only. The age arm lives in the append path and dates a segment by its in-process creation time, falling back to log mtime for one adopted at open. (3) **The enforced default must equal the advertised one.** DescribeConfigs advertised `retention.ms=604800000` as `DEFAULT_CONFIG` while the cleaner treated absent config as retain-forever. Both now read `topic_config_defaults::default_retention_ms()`; `the_enforced_default_is_the_one_describeconfigs_advertises` is the drift guard. **This deletes data that previously accumulated forever** — a topic with no explicit retention now ages out at 7 days, which is what Apache does and what `-1` opts out of.

Two things about that are worth knowing before touching it. **It is leader-gated** via `OwnershipSource` → `Coordinator::owns`: a pass unlinks files on the shared volume, so a non-leader running it is an NFS substrate rule 3 violation and would silly-rename files the real leader holds open (gh #76). The gate degrades to "own everything" with no coordinator (dev/single-broker) and to "own nothing" until the first `assignment.json` load, which delays a sweep rather than skipping it. **And time-based retention dates a segment by its largest record timestamp, falling back to the log file's mtime** — nothing persists a per-segment timestamp (the manifest has no segment list), so `SegmentMeta::max_timestamp` is only populated for segments this process rolled itself; everything inherited across a restart ages by mtime. That is Apache's own fallback (`LogSegment.largestTimestamp` → `lastModified`), not an approximation kaas invented.

The compactor is still absent: `min.compaction.lag.ms` (KIP-58) and `delete.retention.ms` (KIP-354) remain config plumbing only (`topicconfig.rs`, CR → `.config.json` → DescribeConfigs, which advertises a 24 h `delete.retention.ms` default). When compaction lands, tombstone-expiry granularity will be per-batch (Apache is per-record) per the byte-opacity contract.

## Idempotent producer state on disk

The handlers and the txn store are in `crates/kaas-coordinator/CLAUDE.md`.

- **Per-partition sequence tracking** (`crates/kaas-storage/src/idempotence.rs`). Per-PID producer state with a 5-batch ring buffer — mirrors Java's `max.in.flight.requests.per.connection=5`. Classification runs under the partition mutex before append: duplicate (echo cached `baseOffset`, no log write; at `acks=all` it first waits for any flush still outstanding, or a client retrying on a new connection is acked before the original's fsync, gh #321), out-of-order (wire 45), invalid epoch (wire 47), or accept.
- **Snapshot persistence** (`crates/kaas-storage/src/producer_snapshot.rs`). `producer-state.snapshot` next to `manifest.json`; written on take-over and close/relinquish (the same `persist_state_locked` sites as the manifest — not on segment roll); restored on partition open. Without it, broker restart loses the dedupe window and in-flight retries get OUT_OF_ORDER.

## Storage layout

Everything cluster-wide lives in the **cluster-state dir** — `KAAS_CLUSTER_DIR`, default `<data_dir>/__cluster`; the chart's `storage.controlPlane.enabled` mounts it on its own PVC (gh #221 phase 1) so a full data volume can't take the control plane down: `assignment.json` (controller-written, broker-read), `acls.json`, `credentials.json` (operator-written, broker-read with hot-reload), `txn_state/slot-*.json` (gh #22 + #28 — txn coordinator state, slot-sharded; replaces Apache's `__transaction_state` internal topic, see the non-goal in the root `CLAUDE.md`), `producer_fences/from-kaas-*.json` (gh #108 phase 2 cross-broker producer-epoch fence broadcast), `producer_ids/kaas-<id>.json` (gh #219 per-broker PID block high-water; each broker writes only its own), `marker_queue/to-<broker>/` (gh #175 cross-broker txn marker dispatch), and per-group offset files under `__consumer_offsets/<groupID>.json` (moved under `__cluster/` by gh #223 — at the data-dir root the operator's orphan sweep deleted them every pass; the legacy-dir adoption shim was dropped per the pre-v1 no-backcompat policy). The `kaas-controller` Lease lives in K8s (not on the PVC).

**Volume pool (gh #221 phase 2).** `storage.pool[]` in the chart declares additional named RWX volumes ("log dirs", KIP-113 vocabulary), mounted at `/vols/<name>` and advertised via `KAAS_LOG_DIRS` (broker + operator). `KafkaTopic.spec.storage.volumes` binds a topic to an eligible set; the reconciler round-robins new partitions over it and records placement in `status.volumeAssignments` (creation-sticky — spec edits never move data; drift surfaces as `status.partitionsOutsideSpec`). The broker's topic watch stashes assignments into the `TopicRegistry`, which implements the engine's `PlacementResolver`; unknown/unplaced always falls back to the default data dir. **Where the data actually is outranks the placement record (gh #234).** Placement is eventually-consistent — partitions are routinely opened before `status.volumeAssignments` is written — so `partition_dir` resolves: assigned root if it holds a `manifest.json`; else any known root that does (no data movement; it WARNs only when the broker holds a placement record naming another root — at boot it holds none, because takeover runs off `assignment.json` before the topic watch lists, so warning without a record fired for every pool-placed partition on every restart, gh #271); else the assigned root (fresh create). Pre-fix, a restart re-derived the assigned root, found it empty, and half the topic silently came up as fresh 0-byte logs. Only the explicit migration path (`move_partition_to_log_dir`) relocates bytes. gh #224 adds `spec.storage.volumeSelector` (label-match over `storage.pool[].labels`, mutually exclusive with `volumes`) and the `kaas.rs/migrate-to-volume` annotation (level-triggered broker-side drain driver over the AlterReplicaLogDirs path). Topic-level files and the gh #219 identity check are per involved root; the orphan sweep walks every pool root. Book page: `docs/src/architecture/volume-pool.md`.

Per-topic files live at `/data/<topic>/`: `.config.json` (retention/segment/compaction knobs) and `.topic-id.json` (gh #219 incarnation stamp — see `docs/src/code-tour/topic-lifecycle.md`). Per-partition data lives at `/data/<topic>/<partition>/` with epoch-prefixed segment filenames so a stale leader's late writes can't corrupt a new leader's log. Sibling files: `manifest.json` (epoch + HWM + logStartOffset), `producer-state.snapshot` (gh #12 idempotent-producer dedupe window — see "Idempotent producer" in `crates/kaas-coordinator/CLAUDE.md`), and `txn-index.snapshot` (gh #177 read_committed indexes: open-txn first offsets → LSO, aborted list → `AbortedTransactions[]`; same persist triggers and superseded-epoch guard as the producer snapshot, restored on open with aborted entries below logStart evicted).
