## The CRDs

Operator manages 3 CRDs typed in `crates/kaas-operator-api/src/`: `KafkaCluster` (external listener plumbing), `KafkaTopic` (partition dir creation; `Status.TopicID` carries a v4 UUID generated on first reconcile — wire propagation is still open, see "TopicID propagation" in `crates/kaas-broker/CLAUDE.md`; gh #105/KIP-516), `KafkaUser` (auth + ACLs + quotas — `spec.authentication` / `spec.authorization` mirror Strimzi 1:1 since gh #135; materialized to `credentials.json` + `acls.json` under `/data/__cluster/`. **`spec.authentication` is optional (gh #42): an authorization-only user omits it** — an OAUTHBEARER principal has no credential to materialize, so its CR carries only `authorization`/`quotas` and names the principal via `metadata.name` (the token `sub`); the reconciler writes no `credentials.json` entry and only rebuilds ACLs, matching Strimzi's authorization-only oauth users). The `KafkaClusterAssignments` CR that once existed as a reserved debug mirror was removed in v0.3.2-preview — its status writer was never ported from Go (gh #191/#262); read `assignment.json` on the volume instead. **`spec.quotas` intentionally diverges from Strimzi**: the byte-rate fields are named `producerMaxByteRatePerBroker` / `consumerMaxByteRatePerBroker` (vs Strimzi's `producerByteRate` / `consumerByteRate`) to make the per-broker semantics (Apache Kafka 3.7 / KIP-13) legible at the CR level. With N brokers the effective cluster-wide ceiling is N × the configured value — same semantics Strimzi/Apache Kafka have, just named honestly. The pre-gh #135 `KafkaACL` and `KafkaUserGroup` CRs are gone — ACLs are authored inline on each KafkaUser's `spec.authorization.acls` list. To grant the same rule to N principals, repeat the ACL on each of their KafkaUser CRs (no group abstraction; the Strimzi-pattern trade).

## Reconcilers and the leader lease

**Operator reconcilers do NOT use cleanup finalizers.** Earlier versions had `kaas.rs/{topic,user,acl,usergroup,kafkacluster}-cleanup` finalizers that drained on CR delete; ArgoCD's parallel cascade-delete deadlocked when the operator pod went down before its CRs. Cleanup is now reconcile-time (best-effort recursive delete / credentials-file edit when the CR is gone) plus a leader-elected startup sweep (`crates/kaas-operator-controllers/src/`) that drops orphan dirs / stale credential entries the reconciler missed. Owned external resources (Certificates, Services, TLSRoutes) carry `OwnerReferences` so K8s GC handles cluster-CR deletion.

**The operator's leader lease is renewed for as long as it leads, and a standby reads as Ready (gh #329).** It uses the broker's `KubeLeaseElection::campaign`. Until then it called `acquire` once and never wrote the lease again, so a second replica took over 15 s later while the first carried on. **Readiness must not wait for the lease.** A rollout surges the new pod and stops the old one only once the new one is Ready, and the old pod keeps renewing until it's stopped, so a standby that waits for the lease deadlocks the rollout. The missing renewal is what used to hide that. Lost leadership is `process::exit(1)` straight away, with no drain: another candidate may already be reconciling, and the reconcilers are idempotent. SIGTERM stops new reconciles (`Controller::graceful_shutdown_on`; without it every SIGTERM waited for the kubelet's SIGKILL), waits up to `SHUTDOWN_GRACE` (20 s) for running ones **with the lease still held**, then releases it, so no successor starts next to a running reconcile and none waits out the 15 s. `bins/kaas-operator/tests/leader_lease.rs` runs the real binary against a fake API server on loopback. **Its child's environment is cleared on purpose**: `Client::try_default` would otherwise use whatever kubeconfig the machine has.
