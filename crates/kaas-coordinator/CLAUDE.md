## Idempotent producer (gh #12, #22, #30)

The Java producer enables idempotence by default since Kafka 3.0, so every `kafka-console-producer` / `kafka-verifiable-producer` invocation hits this path. Layers of state, all on the shared PVC:

- **InitProducerId handler** (`crates/kaas-broker/src/handlers/init_producer_id.rs`, API key 22, v0–v4). For non-transactional producers (empty `transactional.id`): hands out a fresh PID, epoch=0. For transactional producers: looks up the txn ID in the txn state store and returns the **same PID with epoch+1** on every reconnect — the gh #22 fence-on-rejoin contract. **The v3+ claimed `producer_id`/`producer_epoch` are validated (gh #201, KIP-360, `TxnStateStore::init_producer_id`)**: a stale claim is `PRODUCER_FENCED`, a retry of a claimed bump gets the same answer (the slot entry's `lastEpoch`), and a rejoin that finds an `Ongoing` txn aborts it — `PrepareAbort` at epoch+1, fence, ABORT markers, complete — and answers `CONCURRENT_TRANSACTIONS`. Before that a rejoin left the entry `Ongoing` with the zombie's partitions, so the new session's first commit committed the zombie's records too.
- **PID allocation** (`crates/kaas-broker/src/producer_id.rs`, gh #219). PIDs must never be reused: the dedupe window (`crates/kaas-storage/src/idempotence.rs`) is keyed by `(PID, epoch)`, so a recycled PID lands a fresh producer on a dead producer's sequence history — its batches are then silently dropped as duplicates or rejected with `OUT_OF_ORDER_SEQUENCE_NUMBER`. The pre-gh #219 `AtomicI64::new(1)` reissued PIDs on every restart *and* every broker issued the same ones. Apache uses a quorum-persisted global block allocator; kaas has no quorum (non-goal), so it partitions the space instead: `pid = (broker_id + 1) * 2^40 + local`, with `local` advancing in 1000-PID blocks whose end is persisted to `/data/__cluster/producer_ids/kaas-<id>.json` **before** any PID in the block is handed out (crash → skip forward, never rewind). Each broker is the single writer of its own file — no cross-broker read-modify-write. The `+ 1` keeps broker 0 clear of the legacy low PIDs still sitting in on-disk snapshots.
- **Txn state store** (`crates/kaas-coordinator/src/txn_state.rs`). Per-`transactional.id` `{PID, epoch, state, partitions, groups, ongoingSinceMs, transactionTimeoutMs}` slot-sharded across `/data/__cluster/txn_state/slot-N.json` (50 slots default, matches Apache's `transaction.state.log.num.partitions=50`). Each broker owns the slots that hash to it under gh #91 routing; on coordinator failover the new owner reads the same slot file off the shared RWX PVC (close-to-open consistency = the file IS the materialised state, no log replay needed). This is the architectural answer to gh #29 — see the "literal `__transaction_state` internal topic" non-goal in the root `CLAUDE.md`.
- **Cross-partition fence on bump.** Called from the InitProducerId handler after every `epoch > 0` rejoin: walks every partition, advances the PID's epoch and clears the dedupe window, so a zombie batch from the old session is fenced even on partitions the new session hasn't yet touched. gh #108 phase 2 broadcasts fences across brokers via a per-broker fence log under `/data/__cluster/producer_fences/` (`crates/kaas-coordinator/src/fence_log.rs`); peer brokers' `FenceWatcher` (`crates/kaas-broker/src/fence_watcher.rs`) polls and applies.

The per-partition sequence tracking and its snapshot are in `crates/kaas-storage/CLAUDE.md`.

## Transaction coordinator state machine (gh #23–#28, #37)

Built on top of the txn state store. Handlers in `crates/kaas-broker/src/handlers/`:

- **AddPartitionsToTxn** (key 24, `add_partitions_to_txn.rs`) — `Empty/Complete*` → `Ongoing` stamps `OngoingSinceMs` so the reaper has a deadline clock.
- **AddOffsetsToTxn** (key 25, `add_offsets_to_txn.rs`) — records consumer group IDs that the txn will commit offsets to; same `Ongoing` transition stamps the clock.
- **TxnOffsetCommit** (key 28, `txn_offset_commit.rs`) — stages offsets in a **pending** layer keyed by `(groupID, PID)` in the offset store. They are NOT visible to `OffsetFetch` until commit. Group-coordinator side only (non-coordinators return `NOT_COORDINATOR`). `EndTxn`'s hook fires on the txn coordinator's local store, so when the two coordinators are different brokers the staged offsets are never materialised: duplicates, not loss (gh #340). The handler also doesn't check generation, member or producer epoch (gh #341).
- **Produce verifies a transaction's first batch on a partition (gh #299, KIP-890 part 1).** `ProduceHandler::verify_txn_batch` asks `TxnStateStore::verify_partition`, which reads the slot file directly, so it works when the coordinator is another broker. Without this a delayed retry after an abort, or a producer that never called AddPartitionsToTxn, opens a transaction no marker will ever close, and the LSO stays pinned across restarts. **A yes from the coordinator isn't enough on its own:** the transaction can end while it travels, so `Partition::begin_txn_verification` issues a token, `append_verified` checks it under the partition lock, and any append from that producer clears it, a marker included. That's Apache's `VerificationGuard`, and the batch is refused with 48 if a marker overtook it. **`verify_partition` takes no lock**: a slot is replaced atomically, and this is on the produce path, while the store's mutex can be held across an fsync. The cost is one slot read per transaction per partition, because a producer with an open transaction there skips it, and that depends on replay rebuilding `open_txns` after a crash (gh #303). Marker appends go straight to the engine and aren't gated. Codes follow Apache's two conversions: `PRODUCER_FENCED` becomes 47, and anything that isn't a verdict becomes 19, which the producer retries.
- **EndTxn** (key 26, `end_txn.rs`) — **two-phase, and the phases are the correctness property (gh #225)**: `prepare → dispatch every marker → complete`. `prepare_end_txn` moves `Ongoing → Prepare{Commit,Abort}` and **deliberately retains `Partitions` and `Groups`** — `Prepare*` plus a retained partition list *is* the durable record of "these markers still owe a write", so a dispatch failure, a coordinator crash, or a producer retry all re-derive the identical dispatch set. `complete_end_txn` is the only thing that clears them and fires the txn offset hook (commit → commit pending; abort → discard pending), and the handler calls it **only once every marker is durable**. The hook runs **first**, as `settle_offsets`, right after the prepare and before any marker, and it can fail (gh #318): a commit whose offsets didn't reach the disk stays prepared with its groups and answers 15, and `commit_pending` keeps them staged until the write lands. Before markers because each retry re-appends them otherwise; safe because `Prepare*` already decided the direction. So the hook is idempotent, and **anything staged must be storable**: `AddOffsetsToTxn` and `TxnOffsetCommit` refuse an id too long for a file (24), because a permanent failure here wedges the `transactional.id` until a restart. The hook is `impl TxnOffsetHook for Manager`, and it drops the staged offsets of a group that has moved away rather than rewriting its file from a stale cache. Any dispatch failure returns a retriable `COORDINATOR_NOT_AVAILABLE` and leaves the entry prepared. Before gh #225 the store went straight to `Complete*`, cleared the list, then dispatched best-effort — logging and swallowing every failure while still answering `error_code = 0`. That was unrecoverable by construction: the dispatch set was gone, a producer retry was a documented no-op, and no reconcile existed, so a `read_committed` consumer's LSO pinned forever — not just for the lost txn but for every committed record written to that partition after it. Don't re-collapse the phases, and don't let `complete_end_txn` run on a path that hasn't confirmed durability.
- **WriteTxnMarkers** (key 27, `write_txn_markers.rs`) + **marker queue** (gh #175, `crates/kaas-coordinator/src/marker_queue.rs`, `crates/kaas-broker/src/marker_watcher.rs`). Cross-broker COMMIT/ABORT marker dispatch goes through the shared PVC instead of a wire RPC: the txn coordinator writes one JSON file per `(pid, epoch, target_broker)` under `/data/__cluster/marker_queue/to-<target>/`; every broker polls its own `to-<self>/` directory (2 s default) and applies the markers as control-batch appends — same pattern as the fence log. A successful `enqueue` is the **durability boundary** for a peer partition: the entry is on the shared volume and the peer's `MarkerWatcher` retries until it applies (`ApplyOutcome::Retry` keeps the file), so `EndTxn` may complete once the entry is written. An enqueue *failure* is fatal to that attempt — see the gh #225 note on EndTxn above.
- **Timeout reaper + marker reconcile** (started by the broker at boot, same 10 s tick — Apache's `transaction.abort.timed.out.transaction.cleanup.interval.ms` default). The reaper walks slots and transitions overdue `Ongoing` entries to **`PrepareAbort`** (not `CompleteAbort`), bumping the epoch for gh #22 fencing but **keeping `Partitions`/`Groups`** — a timed-out txn owes ABORT markers exactly like a client-driven one. The reconcile (`crates/kaas-broker/src/txn_markers.rs`, `reconcile_pending_markers` over `TxnStateStore::pending_marker_dispatches`) then places those markers and completes the txn, firing the offset hook. **Both halves are needed and neither subsumes the other** (gh #225): the handler's inline dispatch keeps commit latency off the sweep interval, but only the sweep can finish a txn whose producer crashed, was fenced, or never existed — a reaper-aborted txn has no producer to retry at all. Before gh #225 the reaper cleared the partition list with no marker written and `bins/kaas` merely logged a count of the returned `TxnAbortRecord`s (which don't even carry partitions), so every timed-out transaction pinned its partitions' LSO permanently. A dispatch that still fails is left prepared and retried next pass, deliberately unbounded. **Both sweeps are ownership-gated** (`abort_overdue_owned` / `reconcile_pending_markers`'s `owns_txn`, gh #91) on `Broker::owns_txn` — a txn slot file has exactly one legal writer, its coordinator, so the previously ungated sweep had every broker read-modify-writing the same slot on the shared volume (NFS substrate rule 3). The gate degrades in the safe direction at both edges: `owns_txn` answers `true` when no `Coordinator` is installed (dev / single-broker), so nothing stops being swept, and in cluster mode it answers `false` for everything until the first `assignment.json` load, which delays a sweep by one 1 s poll rather than skipping it.

`bins/kaas/tests/eos_v2.rs` exercises the full KIP-447 consume-process-produce-commit round trip against the in-process broker.

**Coordinator file work stays off the scheduler workers (gh #328).** The offset store and the txn store do synchronous I/O behind locks the next caller waits on across someone else's fsync. On a worker that wait parks every connection the worker drives: one busy group took ApiVersions from 0.5 ms to over 300 ms. So handlers go through `Broker::coordinator_io` / `txn_store_io`, which run on the blocking pool behind a semaphore of `COORDINATOR_IO_THREADS` (256), so queued commits can't take the threads the storage committers fsync on. That covers OffsetCommit, OffsetFetch, DescribeGroups, DeleteGroups, OffsetDelete, JoinGroup's cold load, the purge on a topic delete, every txn store call, the producer fence, the marker-queue write, the reaper's tick, and a new PID block. The trade: past 256 commits queued on one group, other groups' commits queue behind them. The `FenceWatcher` and `MarkerWatcher` get off the workers on their own (a `spawn_blocking` per pass and `tokio::fs`, gh #332), since they're one task each. Produce still parks a worker on the partition mutex during an fsync, for up to one fsync per wait (gh #333). **Keep the store's mutex across the offset hook.** It costs EndTxn latency, but with the hook outside it a settle stalled on an abandoned request could fire after the retry finished and the producer staged its next transaction, committing those offsets early. `crates/kaas-broker/tests/coordinator_io_off_workers.rs` pins each route on a one-thread runtime, where a wait on the worker stops the test itself.

## Consumer-group coordinator routing (gh #92)

`coordinator-of-G` is a **pure function**: `hash(groupID) % numBrokers` with the divisor pinned to the full broker set (NOT `len(alive)`), preferred-slot-down falling back to a deterministic alternate from the alive subset. Mirrors Apache Kafka's `partitionFor(groupId)` (which leases the question to `__consumer_offsets` partition leadership); kaas has no `__consumer_offsets` topic, so we hash directly into the broker set. Implementation in `crates/kaas-broker/src/group_hash.rs`.

Group ownership on the broker `Coordinator` is two-tier: explicit `assignment.json.consumerGroups[]` entries win first (the controller's group balancing writes them; this is the forward-compat lever for sticky-rebalance), hash fallback otherwise. The two converge for stable broker sets, so the hash is the load-bearing path in steady state.

**The two tiers can legitimately disagree, and that is why both halves of gh #248 matter.** An explicit entry is sticky across alive-set changes, so it can name a broker the hash no longer would. So (a) `balance_groups` **carries an entry forward while its broker is alive even when the group is absent from `active_groups()`** — that input is the union over *connected* brokers, and a group drops out of it for reasons unrelated to coordination (members all left for a moment, a stale heartbeat window, an in-memory sweep). Retiring on absence handed the group to the hash, which named a different broker: `NOT_COORDINATOR` → `UNKNOWN_MEMBER_ID` → full rebuild, on a healthy group, triggered by an unrelated topic delete. It was not self-healing either — the next recompute's `prev` no longer had the entry — so one missed report moved a coordinator permanently. Retirement is by broker death, not absence. And (b) **anything resolving a group's coordinator must resolve it the same way**: `GroupTakeoverDriver` read the explicit list alone, so a hash-owned group (every brand-new group, and any whose entry was retired) looked unowned and was relinquished on *every* assignment change — dropping the member list, hence `UNKNOWN_MEMBER_ID`, for a move that never happened. Its sweep now runs over `Manager::resident_groups()` (everything in memory) rather than `local_groups()` (already filtered by ownership, so it structurally could not see the groups the sweep existed to drop). Coordinator transitions are logged in both directions — the 2026-08-06 flap was reconstructible only from the client's log.

**The third defect was the one that fired every time, and it was in the mint path.** `balance_groups` created new entries with `rendezvous_pick_group` (highest-random-weight) while brokers resolved the hash tier with `pick_coordinator` (`hash % n` plus a deterministic alternate). Those agree only by coincidence — on the live 3-broker cluster they disagreed for *every* group id tried. So the first entry the controller ever wrote for a group moved it: the group had been served from wherever the fallthrough said, and the entry named somewhere else. One guaranteed `NOT_COORDINATOR` → rebuild per group, shortly after it started, on a healthy cluster. That is why the streams bench passed on 2026-08-05 and failed on 2026-08-06 with an identical build — the move is once-per-group, so whether it costs duplicates depends only on whether it lands before or after the app has committed work. `balance_groups` now mints with `pick_group_coordinator`, so the entry **confirms** where the group already is. It takes `&[BrokerAssignment]` (the rows the writer is about to serialise) rather than a list of alive ids, because `pick_coordinator` divides by the full registered set (gh #249) and anything narrower reintroduces the divisor bug — passing the rows means both sides resolve from byte-identical input. Test: `a_minted_entry_confirms_where_the_hash_already_put_the_group`.

The coordinator manager's group-assignment source is hot-swapped from `bins/kaas/src/cluster.rs` after the broker `Coordinator` boots — the bootstrap source is an always-true local stub used during the brief window before the runtime is up; tests can substitute their own source. **Don't unwire the swap** without re-reading gh #92: an earlier attempt (v0.1.52) hit the chicken-and-egg (strict coordinator checks block fresh-group bootstrap) and was reverted in v0.1.53.

`GroupTakeoverDriver` (`crates/kaas-broker/src/group_takeover.rs`) runs one sweep over every resident group on assignment change (it subsumes the old prev→next diff — a group can only be relinquished if it is resident). The sweep keeps memory bounded across alive-set churn and fixes the gh #89 stale-`--list` symptom. `ListGroups` and `DescribeGroups` filter by coordinator ownership so a stale group entry on a non-coordinator broker isn't visible to clients via the AdminClient's union across brokers.
